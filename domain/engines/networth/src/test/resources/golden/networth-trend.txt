Golden file for :domain:engines:networth's trend (issue 6.6; FR-ACC-005).

Every record is one series of STORED daily snapshots and the trend read off it. Amounts are PAISE
(MNY-001), never rupees -- a fixture written in rupees is a fixture that silently passes at a
hundredth of the amount it claims. The percentage change is integer BASIS POINTS (MNY-002): 2500 is
25.00%, not 2500%.

WHERE THESE NUMBERS COME FROM: an independent Python implementation written from the specification
and not from the Kotlin it guards. Agreement between the two is therefore evidence the figures are
RIGHT, not merely unchanged. A golden file regenerated from the code it checks asserts only that the
code has not moved, which is a different and much weaker claim.

THE FIVE RECORDS THAT ARE THE POINT OF THIS FILE are the ones where a percentage must be REFUSED.
Net worth is routinely negative for a user with a loan and little saved, and -50,00,000 paise moving
to -10,00,000 paise is an improvement of 40,00,000 paise -- it is NOT "+80%", and reporting it as
one would be a fabricated figure in the position a user trusts most (P-03). The rule is that a
percentage is reported only when the STARTING value is strictly positive: `> 0`, never `>= 0`,
because a zero denominator is the same lie by a different route. Those records are `negative
throughout`, `crossing zero`, `starting at exactly zero`, plus the two single/empty cases where
there is no interval to measure at all.

A change over a ZERO-LENGTH interval is absent, not zero. One reading tells you what net worth was
that day and nothing whatever about which way it is going, so `expect_change=none` -- the same
distinction the dashboard already draws between "no snapshot yet" and a net worth of zero.

Ties on high and low resolve to the EARLIEST point, so a flat series names its first day rather than
an arbitrary one, and the file stays reproducible to the byte (P-08).

Record format -- one `# key=value` per line, then one payload row per snapshot, records separated by
a line of `===`:

  label           what the case is for, quoted back in assertion failures
  expect_first    `iso_date:paise` of the earliest point, or `none` for an empty series
  expect_last     `iso_date:paise` of the latest point, or `none`
  expect_change   last minus first, in paise, or `none` when there is no interval
  expect_bps      integer basis points, or `none` when a percentage would mislead
  expect_high     `iso_date:paise` of the largest value, earliest on a tie, or `none`
  expect_low      `iso_date:paise` of the smallest value, earliest on a tie, or `none`
  expect_points   how many rows the record carries, so a dropped row cannot pass unnoticed

  payload row: as_of_iso_date|net_worth_minor
               net_worth_minor is SIGNED -- negative is a user who owes more than they hold

No clock is read and no order is incidental. The engine receives points already bounded to the
requested range; choosing that window is the repository's job, because it needs a clock (TIM-001).
