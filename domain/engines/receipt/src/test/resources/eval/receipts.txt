# =============================================================================
# Frozen receipt evaluation set — the ≥ 95% total-amount gate (issue 3.8; SRS §18.1, §21.5).
#
# Why:  §18.1 sets two numeric targets — "total-amount accuracy ≥ 95% on printed receipts,
#       ≥ 80% field-complete extraction" — and §21.5 says AI evaluation runs against frozen
#       labelled datasets with regression thresholds that block merges. ReceiptEvalTest is that
#       gate. These are the receipts; the labels are what a person reads off them.
# What: forty-six anonymised receipt texts of the kind ML Kit returns for Indian printed bills —
#       supermarkets, restaurants, fuel, pharmacy, e-commerce, autos, utilities — each labelled
#       with the total in paise, the date and the merchant. The last six are deliberately awkward;
#       see the comment above them.
# Result: changing a heuristic and losing accuracy fails the build.
# Changelog: 2026-08-06 — Created for issue 3.8.
#
# **What this set does and does not prove.** It was written alongside the parser, so its 100%
# total-amount score is *not* an independent estimate of how the app performs on a real photograph
# — it is regression protection: a heuristic edit that breaks one of these shapes fails the build.
# The independent measurement is the device run, against receipts nobody wrote for this file.
#
# **A text file, not JSON, on purpose.** `:domain:*` is pure Kotlin with no serialisation
# dependency (ARC-002), so a JSON fixture would mean hand-rolling a parser in a test — thirty
# lines of bracket counting whose bugs would look like parser bugs. This format is read by six
# lines of `split`.
#
# **Every amount here is invented.** No real person's receipt is in this repository (P-01).
#
# Format: `# key=value` header lines, then the recognised text, then `===` on its own line.
#         `date=` and `merchant=` may be empty, meaning the receipt genuinely does not show one.
# =============================================================================
