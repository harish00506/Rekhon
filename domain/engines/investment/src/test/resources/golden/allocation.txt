Golden file for :domain:engines:investment's allocation (issue 6.4; FR-INV-002, RULE-GOLD-CAP v1.0,
RULE-CRYPTO-CAP v1.0, RULE-CONC-15-70 v1.0).

Every record is one whole portfolio. Amounts are PAISE (MNY-001), never rupees -- a fixture written
in rupees is a fixture that silently passes at a hundredth of the amount it claims. Shares are
integer BASIS POINTS (MNY-002): 1010 is 10.1%, not 1010%.

WHERE THESE NUMBERS COME FROM: an independent Python implementation written from the specification
-- largest-remainder apportionment over integer basis points -- and not from the Kotlin it guards.
Agreement between the two is therefore evidence the shares are RIGHT, not merely unchanged. A golden
file regenerated from the code it checks asserts only that the code has not moved, which is a
different and much weaker claim.

The first two records are the boundary pair, and they are the reason this file exists. The rulebook
says "Gold <= 10%" and "Single holding <= 15%", so a portfolio sitting exactly on both lines has
nothing to answer for and a portfolio one basis point past either one does. Off-by-one is the
single most likely bug in a threshold engine and the least likely to be noticed, because both
versions look correct in a screenshot.

Record format -- one `# key=value` per line, then one payload row per position, records separated
by a line of `===`:

  label               what the case is for, quoted back in assertion failures
  expect_total        paise across the priced positions -- the denominator
  expect_slices       `class:paise:bps` comma-separated, largest first, or `none`
  expect_flags        `KIND:subject:measured_bps:threshold_bps` comma-separated, in order, or `none`
                      subject is the AssetClass storedValue for a class flag, the position's name
                      for a SINGLE_HOLDING flag
  expect_valued       positions that carried a price and were counted
  expect_unvalued     positions excluded for having none (P-03)
  expect_unavailable  an AllocationUnavailable name, or `none` when there is a split

  payload row: holding_id|account_id|name|asset_class|value_minor
               holding_id `none` means the position IS an account counted whole
               value_minor `none` means never priced -- absent, which is NOT zero (P-03)

Flags are ordered narrowest rule to broadest: the class caps first, then single-class, then
single-holding, and within single-holding largest share first with ties broken by name. A user
reading top-down should meet "gold is past its own ceiling" before "something is over 70%".

The whole file is reproducible to the byte (P-08): no clock is read and no order is incidental.
