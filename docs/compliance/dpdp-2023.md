# DPDP Act 2023 — alignment

**Status:** the app's own obligations are met in code. **Four obligations are the publisher's, not the
code's, and are open** — see [§4](#4--open-the-publishers-obligations-not-the-codes). This document is
not legal advice; it is an engineering traceability record.

**Scope.** AI Personal CFO is offline-first (P-04) and stores everything in one encrypted database on
one device (P-01). There is no server holding user data, no account, and no telemetry. That shapes
every row below: most obligations are met **structurally** — the processing that would trigger them
does not happen — rather than by a procedure someone has to remember to follow.

**The checkable claim.** Every file and test named in this document is asserted to exist by
`core/datastore/src/test/kotlin/com/aicfo/core/datastore/DpdpComplianceDriftTest.kt`. If a class is
renamed or a test deleted, the build fails rather than this document becoming quietly untrue.

---

## 1 · Purpose limitation (§4, §6(1) — consent limited to what is necessary)

Each optional data flow is a separate, revocable consent with its purpose stated **where the user
grants it**. The purpose is a string resource, so it is translated and cannot drift into a comment.

| Consent (`ConsentFeature.id`) | Purpose, as shown to the user | What leaves the device | Enforced in |
|---|---|---|---|
| `sms_parsing` | Read bank/UPI messages to suggest transactions, so they need not be typed | **Nothing.** Parsing is on-device | `SmsRepository`, `SmsConsentWatcher` |
| `market_data` | Fetch gold, crypto and fund prices so holdings can be valued | **Only a `PriceKey`** — an instrument identifier whose character set cannot hold an amount or a name | `MarketPriceRepository` |
| `cloud_llm` | Would let the assistant ask a cloud model when the on-device one cannot answer | **Nothing — there is no transport.** Listed and described as unbuilt rather than hidden | nothing; the dashboard says so |
| `account_aggregator` | Pull bank statements through India's AA framework, so transactions need not be typed or parsed from SMS | **Nothing leaves** — the flow is inbound. The app's gate sits in front of the AA framework's own consent artefact, so revoking here stops the app asking even while an AA consent is live. **Designed, not built** (issue 13.6, ADR-0074) | nothing yet; `AccountAggregatorApi` is an unconfigured stub |
| `cloud_backup` | Write an encrypted backup off this device | **Only ciphertext**, sealed with the user's own passphrase before it leaves | `BackupRepository` |

- Default is **off** for every one of them (`ConsentState.NOT_GRANTED`), which is §6's "clear
  affirmative action" rather than a pre-ticked box.
- The purpose and the **consequence of withdrawal** are both shown per consent on the dashboard
  (issue 11.3): `ConsentFeature.purpose()` and `ConsentFeature.whenWithdrawn()`, each a `when` over
  the enum, so a consent added without wording cannot compile.
- **No off-device processing without a consent basis (AC3).** `UnconfiguredMarketDataApi` is the
  default binding: with no configured base URL the app makes no network call at all, and the only
  configured call is consent-gated and carries no personal data.

## 2 · Notice (§5)

| §5 requirement | Where |
|---|---|
| Notice **at or before** consent | Onboarding step 1, before any data is entered: `onboarding_welcome_pledge_title` / `..._pledge_body` |

## 3 · Data-principal rights

| Right | DPDP | How it is exercised | Implementation | Proof |
|---|---|---|---|---|
| **Access / know** | §11 | Settings → export writes a JSON archive of every table the profile owns, **plus the consent record**: what was allowed and since when | `ArchiveRepository.export`, `ConsentRecord` | `ArchiveConsentRecordTest`, `ArchiveRepositoryTest` |
| **Portability** | §11 | The same file: plain JSON the user owns and can read, not a proprietary blob | `CfoArchive` | `ArchiveFormatTest` |
| **Correction** | §12(1) | Every record the app holds is editable or deletable in the UI that created it; derived figures are recomputed, never stored as fact | `TransactionRepository`, `AccountRepository` | `TransactionRepositoryTest` |
| **Erasure** | §12(2) | Settings → Erase everything: the Keystore keys are destroyed, so the ciphertext is unrecoverable, then the files go | `EraseRepository`, `AndroidSecureEraser` | `EraseRepositoryTest`, `AndroidSecureEraserTest`, `EraseDeviceTest` |
| **Withdraw consent** | §6(4) — with "comparable ease" | The same one tap that granted it, on the same screen | `ConsentsViewModel` | `ConsentsViewModelTest` |
| **Grievance redressal** | §13 | **Open** — see §4 | — | — |
| **Nomination** | §14 | **Open** — see §4 | — | — |

Withdrawal is not merely recorded: each dependent path stops at the next read, and two of them
actively clean up — revoking `sms_parsing` erases pending drafts and resets the scan cursor;
revoking `cloud_backup` drops a backup waiting to be written. Asserted in `SmsRepositoryTest` and
`BackupRepositoryTest`.

## 4 · Open: the publisher's obligations, not the code's

These are **not satisfied** and cannot be satisfied by code in this repository. They are listed so
the gap is on the record rather than implied away by the rows above.

| Obligation | DPDP | Why code cannot close it | What is needed before a public release |
|---|---|---|---|
| **Grievance redressal** | §13 | Requires a named contact and a response process | A published contact address and a stated response time, surfaced in Settings |
| **Nomination** | §14 | Requires a mechanism for a nominee to act on the principal's behalf | A product decision; for a device-local app with no account, likely out of scope — but that reasoning has to be written down, not assumed |
| **Breach notification** | §8(6) | Requires an operator process and a route to the Board | An incident procedure. Note the app's structural position: with no server and no collected data, there is no central store to breach |
| **Children's data** | §9 | Requires verifiable parental consent and no tracking of children | Either an age gate or a documented decision that the app is not directed at children. The app does no tracking and shows no ads, which covers §9(3) |

**Also deliberately deferred** (recorded in ADR-0061): an append-only consent *history* rather than
the latest grant/withdraw pair per feature — the ledger keeps one of each by design (issue 1.9), and
turning it into a log is a schema change plus a retention decision; and a pre-erase "here is what we
held" summary, since the export already produces exactly that and asking the user to take one before
erasing would be a nag, not a right.

## 5 · Security safeguards (§8(5))

Not a DPDP-specific build, but the obligation is cited here so the matrix is complete:
SQLCipher at rest with the key in the Keystore or StrongBox (ADR-0057), `FLAG_SECURE` on every screen
(ADR-0058), Tink-only cryptography with no hand-rolled primitives (SEC-003), and PII/amount logging
blocked by a lint rule that fails the build (`CfoPiiInLogs`).
