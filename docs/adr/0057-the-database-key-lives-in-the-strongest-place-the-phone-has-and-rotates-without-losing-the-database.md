# ADR-0057 — The database key lives in the strongest place the phone has, and rotates without losing the database

- **Status:** accepted
- **Date:** 2026-09-28
- **Deciders:** Harish G (solo)
- **SRS refs:** §23 (security), SEC-003 (Tink/Keystore only, no hand-rolled crypto), DB-003, P-01,
  P-04; issue 11.1. Supersedes the StrongBox note written into `KeystoreAeadFactory` at issue 1.6.

## Context

Issue 1.6 built the key path: a random SQLCipher passphrase, wrapped by a Tink AEAD whose master
key lives in the Android Keystore, with only ciphertext on disk. Issue 11.1 asks for two things it
did not do — **StrongBox where the device has it**, and **a rotation that actually rotates**.

The second is the sharper one. `rotate()` existed and minted a new passphrase, but nothing re-keyed
the file: the first caller would have replaced the key to a database that was still encrypted with
the old one, and locked the user out of every transaction they had ever recorded. It was never
called, which is the only reason it never happened.

## Decision

**1. The master key is generated by the platform, StrongBox first, before Tink looks for it.**
Tink's `AndroidKeysetManager` creates the master key itself and has no StrongBox option, so a phone
with a dedicated security chip was getting an ordinary TEE key. `KeystoreMasterKey` now asks the
platform's own `KeyGenerator` for the key at that alias first, with `setIsStrongBoxBacked(true)`
where the device advertises `FEATURE_STRONGBOX_KEYSTORE`; Tink then finds it and uses it.

- **This is not hand-rolled crypto, and the 1.6 note that said it was has been corrected.** Nothing
  here implements a cipher, a mode, a padding or a derivation. The Android Keystore generates and
  holds the key, exactly as it did when Tink made the same call — the difference is one builder
  flag that moves it into better hardware. Reading SEC-003 as forbidding *configuration of the
  platform keystore* would mean the rule forbids the strongest thing it exists to encourage.
- **An existing alias is never replaced.** This is the decision that protects every installation
  that already has data: Tink's keyset is encrypted with the master key, the passphrase is wrapped
  with the keyset, and the database is encrypted with the passphrase. A new key at the same alias
  is silent, total, unrecoverable data loss, on an *upgrade* rather than a fresh install.
  `MasterKeyPolicy` is a pure function with that as its first branch, so it is testable and legible.
- **A refusal is not a failure.** Devices advertise StrongBox and then throw
  `StrongBoxUnavailableException` for particular specs. The fallback is the TEE key the app would
  have had anyway; treating it as fatal would brick the app on those phones.

**2. Rotation is a two-slot protocol, and the file is re-keyed in the middle of it.**
A rotation is two writes that must agree — the file's own encryption and the wrapped passphrase on
disk — and a process can die between them. Whichever order you pick, one crash window leaves the
file encrypted with a key that is nowhere on disk.

So the new key is written to a **pending slot before** the re-key and promoted **after** it:

```
unwrap current → mint new → write pending → PRAGMA rekey → promote pending
```

Every instant of that sequence has both keys on disk. A crash anywhere inside it is recovered on
the next open, which tries the current key and then the pending one and reports back which worked
(`confirm`) — promoting the pending key means the re-key had completed, anything else means it had
not and the staged key is discarded. A re-key that *reports* failure rolls the staging back, because
the file is still on the old key and a staged key that opens nothing would be offered for ever.

- **The promotion is a rename**, so it cannot be interrupted between deleting one file and writing
  the other — the state where neither key exists.
- **The re-key is SQLCipher's own `changePassword`**, not a hand-built `PRAGMA rekey` string.
  Composing the SQL ourselves would mean formatting key material into text, which is a worse
  implementation and one more place a key could be logged.
- **`rotateKey` requires that no `CfoDatabase` is open.** A re-key rewrites every page; another
  connection would read the file as it changed. That contract is documented on the function rather
  than enforced, because enforcing it needs an open-instance registry this app does not have —
  recorded here as the one sharp edge, and the reason no UI calls it yet.

**3. A key that no longer opens anything stops existing in memory.**
From the security review: after a successful rotation the old passphrase is zeroed, and after an
open the candidate that did *not* work is zeroed. Not a defence against a debugger — SQLCipher
holds the live key regardless — but a dead key in a heap dump is cost with no benefit. After a
**failed** rotation the old key is deliberately left intact: the file still needs it.

## What the review checked, and what it found

Run with the `security-review` skill over the diff (SEC-003 requires it for crypto changes).

- **No high-confidence vulnerabilities.** No hardcoded keys, no weak algorithm, no predictable
  randomness (`SecureRandom`, never the injected seedable source — P-08's rule is for engines, and
  a predictable key is a vulnerability), no key material in logs or in SQL text, AES-256-GCM
  throughout, and the wrapped passphrase is bound to its purpose by associated data.
- **One assumption verified rather than assumed:** SQLCipher 4.6.1 does **not** zero the caller's
  passphrase array — checked in the artifact's bytecode, not inferred. Had it done so, trying the
  second candidate after the first, and then confirming which one worked, would both have operated
  on a zeroed array. The recovery path depends on this, so it is written down.
- **Two defence-in-depth findings, both fixed:** the dead-key zeroing above.
- **One accepted constraint:** `rotateKey`'s no-open-database contract.

## Deferred, and why

- **A UI that rotates the key.** The path is proved end to end on a device, but nothing in the app
  offers it: rotation belongs beside erase-all and the consents dashboard (issues 11.3, 11.4),
  where a user can be told what it does. Shipping a button before that would be a security control
  with no explanation attached.
- **StrongBox itself is unproven on hardware.** The emulator does not have it (`API 36`,
  `FEATURE_STRONGBOX_KEYSTORE` absent), so what ran was the fallback. The StrongBox branch is one
  builder flag inside a tested decision, and the instrumented test reports which path it took —
  but it has not executed on a phone that has the chip, and this ADR says so rather than implying
  otherwise.
- **Re-keying the Tink keyset, and key expiry.** SEC-003 asks for a rotation path; it does not ask
  for a schedule. A cryptoperiod is a policy decision with a UI attached, and belongs with the one
  above.
- **Zeroing the live passphrase.** It cannot be: SQLCipher needs it for the life of the connection.

## Consequences

- On a fresh install with StrongBox, the key that wraps everything else lives in a separate chip;
  everywhere else it is TEE-backed exactly as before; and no existing installation's key is touched.
- The database key can be rotated, and the file is re-keyed with it — proved on a device, with
  every row still readable afterwards and the old key no longer opening the file.
- No sequence of crashes during a rotation leaves the database unopenable.
- A key the app has finished with does not linger in its heap.
