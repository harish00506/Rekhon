## 3. Objective — what this task will do
Add a `@JvmInline value class Money(val minor: Long)` in `:core:model` with safe arithmetic
(`plus`, `minus`, `times` by count), `percentOf(bps: Int)` using `RoundingMode.HALF_EVEN`, and a
`split(intoParts)` / `allocate(weights)` that distributes the remainder so the parts **sum exactly**
to the original. Formatting is **not** here — that lives at the UI edge (`MoneyFormatter`).

**Why now / rationale:** it is imported by every engine, repository, and screen; getting rounding
and splitting exact here prevents rupee-drift bugs everywhere.

## 4. Scope
**In scope**
- `Money` type, arithmetic, `percentOf(bps)`, `split`/`allocate` with remainder distribution,
  overflow-checked `plus`/`minus` (`Math.addExact`), `ZERO`, comparison.
- Basis-point helpers (`bps` conversions) in `:core:model`.

**Out of scope (`/ponytail`)**
- Currency conversion/FX (uses cached rates elsewhere, §34.2). Locale formatting (UI edge).
  Multi-currency arithmetic (a `Money` is single-currency; currency is tracked alongside).

## 8. Implementation notes
```kotlin
@JvmInline
value class Money(val minor: Long) : Comparable<Money> {
    operator fun plus(o: Money) = Money(Math.addExact(minor, o.minor))
    operator fun minus(o: Money) = Money(Math.subtractExact(minor, o.minor))
    operator fun times(count: Int) = Money(Math.multiplyExact(minor, count.toLong()))
    fun percentOf(bps: Int): Money            // minor * bps / 10_000, HALF_EVEN
    fun split(intoParts: Int): List<Money>    // parts sum EXACTLY to this; remainder spread 1 paise each
    fun allocate(weights: List<Int>): List<Money> // largest-remainder method; sums exactly
    override fun compareTo(other: Money) = minor.compareTo(other.minor)
    companion object { val ZERO = Money(0) }
}
```
- Use `java.math.RoundingMode.HALF_EVEN` for `percentOf`; implement `allocate` with the
  largest-remainder (Hamilton) method so no paisa is created or lost.

## 9. Acceptance criteria
- [x] **AC1** — Given any `Money` and `intoParts=n>0`, when `split(n)`, then the parts sum **exactly** to the original (no lost/created paise). *(property-swept over ~41 000 amount × part-count combinations, seeded)*
- [x] **AC2** — Given `Money(100_00).percentOf(250)` (2.5%), then result is `Money(250)` (₹2.50), HALF_EVEN. *(tie cases pinned in both directions, positive and negative)*
- [x] **AC3** — Given arithmetic that would overflow `Long`, when `plus`, then it throws `ArithmeticException` (fail fast — not silent wrap). *(also `minus`, `times`, `percentOf`)*
- [x] **AC4** — There is **no** `Double`/`Float`/`BigDecimal` field or param on the public API. *(`BigDecimal`/`BigInteger` appear only as internal locals inside `percentOf`/`MoneyFormatter`)*

**Deviation from §4 (approved):** `MoneyFormatter` ships here rather than at the UI edge — issue 1.2
AC3 requires Indian digit grouping, and `java.text`/`BigInteger` are JVM stdlib, so `:core:model`
stays Android-free (ARC-002). `DecimalFormat` could not do it: it supports only one grouping size and
emitted `₹123,456.78`, so the 2,2,3 rule is written out explicitly.

## 12. Risks & edge cases
- Silent `Long` overflow → use `Math.*Exact`. Rounding ties → HALF_EVEN, test the exact tie.
- Remainder distribution off-by-one → largest-remainder method, property-tested to sum exactly.
- Negative amounts (refunds) must behave (split/allocate defined for negatives too).
