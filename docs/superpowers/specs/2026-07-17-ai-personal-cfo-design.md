## 1 Overview

**AI Personal CFO** is an Android-first, AI-driven personal-finance app for India that behaves
like a full-time CFO: it **classifies, forecasts, advises, and — always — explains**, on-device
and privacy-first. It is **greenfield**: this spec and the SRS exist; the Kotlin/Gradle code is
being written to them.

**Product shape (SRS §1, §5):**

- A single user (later: household and business profiles — §27) tracks accounts, transactions,
  budgets, loans, investments, goals, and an emergency fund.
- A layered **AI engine stack** turns that ledger into categorisation, a cash-flow forecast, a
  financial-health score, a Safe-to-Spend figure, a purchase advisor, and an on-device chat
  assistant.
- Everything works **offline** (P-04). The only network use is a thin, optional backend proxy
  for market data (NAVs, rates, fuel prices) — never a core path (§16, §22).

**Non-negotiables (SRS §1.3 → CLAUDE.md §1):** numbers come from deterministic math, words from
the AI; every output shows its work; no financial data leaves the device without explicit,
revocable, per-feature consent; the app advises but never moves money.

## 2 Guiding Principles (binding — SRS §1.3, CLAUDE.md §1)

| ID | Principle | Engineering consequence |
|----|-----------|--------------------------|
| **P-03** | Numbers from math, words from AI | LLMs never compute an amount/score/forecast. Deterministic engines produce every figure; the LLM only verbalises, gated by the guardrail. |
| **P-01** | Privacy first | No financial data leaves the device without explicit, revocable, per-feature consent. Default fully offline. |
| **P-04** | Offline-first | Every core feature works in airplane mode. Build + tests pass with the backend absent. Network features degrade to cached data + staleness labels. |
| **P-07** | Advice, never orders | The app recommends and simulates; the user decides. No auto-executed money movement in v1. |
| **P-08** | Deterministic & testable | Every engine: fixed input → fixed output. Randomness only via an injected, seedable source. |
| **P-02** | Show the work | Every recommendation shows inputs + the rule/model that fired + a plain-language reason. No black-box verdicts. |
| **P-06** | India-native | INR paise, lakh/crore grouping, FD/RD/PPF/EPF/NPS/ELSS, RBI/AMFI data, DPDP 2023. |
| **AI-ARC-004** | Guardrail every LLM output | LLM text passes the numeric guardrail (`ai/chat/guardrail.md`) before display. |

> **Rule of thumb (CLAUDE.md §5):** prefer the boring, testable, explainable option. Cleverness
> is a cost.

## 3 Users & Roles

- **Primary user** — one person managing their money on their own device. No account, no login
  to a server; the "identity" is the device + biometric/PIN lock (§23).
- **Profiles (design-for, §27)** — the data model is scoped so a **household** (multiple
  profiles) and later a **business** book can be added without a rewrite. v1 ships single-profile
  behind that scoping (Epic 13.1, 13.5).
- **No server-side roles.** The optional backend (§22) is a stateless market-data proxy; it holds
  no user financial data and has no per-user accounts.

## 4 AI Architecture (SRS §7, `ai/architecture/ai-architecture.md`)

The AI is a **layered pipeline, not one model.** Layer N depends only on layers below it:

```
L1 data        raw ledger (accounts, transactions) — the only source of numbers
L2 analytics   deterministic aggregates (spend by category, cash position, ratios)
L3 rules       versioned rulebook rows (ai/rules/*) — thresholds, order-of-operations
L4 predictions recurring detection, cash-flow forecast, seasonality, vehicle costs
L5 decisions   health score, Safe-to-Spend, goal feasibility, purchase advisor
L6 LLM         verbalises L2–L5 output; never computes — guardrailed (AI-ARC-004)
```

**Binding architecture rules (AI-ARC-\*):**

- **AI-ARC-003 Provenance on everything.** Every engine result carries
  `engineId, engineVersion, inputWindow, computedAt, confidence, evidence`.
- **AI-ARC-006 Reproducibility.** Engine versions are stored with each result so old insights
  stay reproducible; thresholds are versioned data rows in `ai/`, cited by ID.
- **AI-ARC-004 Guardrail.** Any LLM-verbalised figure is checked against engine provenance and
  blocked/repaired on mismatch.
- **P-03 / P-08.** Engines are pure, deterministic, and unit-testable; the LLM is a thin
  presentation layer over their output.

**Runtime AI files the app loads** (data, not code — CLAUDE.md §6): the Insight Orchestrator
workflow + engine registry (`ai/orchestrator/`), the rulebook and financial order of operations
(`ai/rules/`), the chat tool registry + system prompt + guardrail (`ai/skills/`, `ai/chat/`), and
the classification / market-signal / tax / seasonality / vehicle knowledge bases (`ai/knowledge/`).
See [`ai/README.md`](../../../ai/README.md).

## 5 Data Model (SRS §11, §20)

- **Store:** Room over **SQLCipher** (encrypted), key in the Android **Keystore** (§23). Fully
  on-device; opens and round-trips in airplane mode.
- **Entities (indicative):** `profile`, `account` (bank/cash/wallet/card/loan/investment),
  `transaction` (+ splits, transfers, source, provenance), `category` + merchant rules, `budget`,
  `goal` + contributions, `emergency_fund`, `investment_lot`, `net_worth_snapshot`, `insight`,
  `consent`, `audit_log`.
- **Invariants:** money is `Long` **paise** in every column that holds an amount (MNY-001);
  soft-delete via `deleted_at`; per-profile scoping on every row; **no destructive migrations**
  (DB-003) — every version bump ships a migration test against a real schema fixture (§21.5).
- **Portability:** a full **local JSON export/import** archive (§5.10, §34) is the user-owned
  backup; there is no cloud copy by default.

## 6 Module Structure (SRS §21.2, §7.1 — binding)

**Dependency is one-way:** `feature → domain → data/core`. Feature modules never depend on each
other; cross-feature navigation goes through the nav graph with typed routes (ARC-001).

```
:app                      single-activity Compose host, nav graph, Hilt graph
:core:model :core:common  pure Kotlin/JVM — Money, Clock, Result, DispatcherProvider (ARC-002)
:core:database            Room + SQLCipher, DAOs, migrations
:domain:engines:*         pure-Kotlin engines (one interface + result types each, ARC-003)
:data:repository          the ONLY classes that touch DAOs or network (ARC-005)
:feature:*                Compose screens + ViewModels (StateFlow UiState, ARC-004)
:ml:ocr :ml:llm           ML Kit OCR, on-device LLM behind interfaces
:sync:backup              E2EE backup/restore
:widget                   Glance home-screen widget
```

- `:core:model` and `:domain:*` are **pure Kotlin (JVM), no Android imports** — enforced by
  Gradle (ARC-002). This keeps engines portable (KMP-ready, §27) and fast to unit-test.
- **Every engine = exactly one public interface + result types;** the implementation is
  `internal`, Hilt constructor-injected (ARC-003, no service locators).
- **UI state** = one immutable data class per screen as `StateFlow`; events flow up via a sealed
  interface (ARC-004). No LiveData, no leaking mutable state.
- All async work uses injected, structured-concurrency scopes; `GlobalScope` is lint-banned
  (ARC-006).

## 7 Money & Time Rules (SRS §21.4 — review-blocking)

- **MNY-001** — Money is `Long` minor units (paise) end-to-end (DB → engine → UI) via the `Money`
  value class. **Any `Double`/`Float` touching a monetary value fails review.** Division uses
  explicit **HALF_EVEN** rounding + remainder distribution so splits always sum.
- **MNY-002** — Percentages/rates are integer **basis points (bps)** in engines.
- **TIM-001** — Timestamps are UTC epoch millis. All calendar logic (day rollover, month
  boundary, due dates) uses the profile time zone via an **injected `Clock`** — never
  `System.currentTimeMillis()` in domain code (lint-banned).
- **TIM-002** — Date-only fields are ISO `LocalDate` strings, never midnight timestamps.

These two areas are the classic bug factories; custom lint (issue 1.5) fails the build on
violations, and the `money-time-audit` skill scans every diff that touches amounts or dates.

## 8 Security & Privacy (SRS §23)

**Threat model:** device loss/theft, shoulder-surfing, screen-sharing/screenshots, malicious
apps, and (for the optional backend) network interception. The app holds a user's entire
financial life, so the store is encrypted and the UI is capture-guarded.

- **At rest:** SQLCipher DB, key in Keystore/**StrongBox**; **no hand-rolled crypto — Google
  Tink / platform Keystore only (SEC-003, review-blocking).**
- **Access:** BiometricPrompt (class 3) + PIN fallback; fail-secure on every error.
- **On screen:** privacy-blur toggle (hide all amounts) + **FLAG_SECURE** on sensitive screens;
  amounts hidden in the app switcher.
- **Consent (P-01):** every optional data path (SMS parsing, network market data, backup, cloud
  LLM) is behind an **explicit, per-feature, revocable** consent row (Proto DataStore); a consents
  dashboard offers one-tap revoke.
- **Backup:** end-to-end encrypted (Argon2id KDF → AES-256-GCM via Tink); the platform never sees
  plaintext or the key.
- **Erase:** crypto-shredding — destroy the Keystore key to render ciphertext unrecoverable, then
  wipe.
- **Logging:** PII/amount logging is banned in release (lint strips it); security events go to
  `audit_log`.
- **Compliance:** aligned to India's **DPDP Act 2023** — purpose limitation, consent records,
  data-principal rights (access via export, erasure via erase-all) (§32).
- **Supply chain:** dependency scanning (OSV) in CI; minified (R8) release (SEC-007).

## 9 Build, CI & Release (SRS §21.3, §21.6, §26)

- **Build:** Gradle multi-module, one **version catalog** (`libs.versions.toml`) pinning the
  §21.3 stack. `:core:model`/`:domain:*` are pure-Kotlin/JVM (ARC-002, Gradle-enforced).
- **Pinned stack (do not swap without an ADR):** Compose + Material 3; Room + SQLCipher; Proto
  DataStore (SharedPreferences banned); Hilt; WorkManager; Retrofit + OkHttp +
  kotlinx.serialization (cert-pinned to our backend); ML Kit Text Recognition v2; AICore/MediaPipe
  for the on-device LLM behind `LlmEngine`; Google Tink; BiometricPrompt.
- **CI (GitHub Actions, [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml)):** build ·
  unit + coverage (`koverVerify`) · ktlint/detekt · Paparazzi screenshot diff · dependency scan ·
  (where a device is available) instrumented E2E. All gates green before merge (§21.6).
- **Trunk-based:** `main` is always releasable; **conventional commits** each referencing their
  requirement ID(s); feature-flag incomplete work — no long-lived branches. Work happens on
  `feature/<id-dashes>-<slug>` and merges to `main`.
- **Versioning (SemVer):** single source of truth is repo-root [`VERSION`](../../../VERSION); keep
  `app/build.gradle.kts` `versionName` equal to it. **New epic → minor bump; finished issue →
  patch bump**, with a [`CHANGELOG.md`](../../../CHANGELOG.md) entry citing requirement IDs. Epics
  map to the SRS roadmap (§26) and traceability (§28).

## 10 Testing Strategy (SRS §21.5 — no feature is done without it)

- **Engines:** golden-file tests (fixed input snapshot → expected result JSON), property tests
  (splits sum, forecast monotonic identities), seeded-determinism tests. **Coverage ≥ 85 %; money
  math 100 %.**
- **Repositories:** Room in-memory + a migration test against a real schema fixture for **every**
  version bump. Destructive migrations forbidden (DB-003).
- **ViewModels:** Turbine on `StateFlow`; assert the full `UiState` sequence incl. loading/error.
- **UI:** Compose tests for critical flows (add txn ≤ 3 taps, onboarding, purchase advisor);
  Paparazzi screenshot tests for design-system components in light/dark/200 % font.
- **AI evaluation:** **frozen labelled datasets** — categorisation ≥ 92 %, receipts ≥ 95 %,
  forecast backtests. Regression thresholds **block merges.**
- **The real gate:** a green build is not "done". Every issue is **run and observed working** on
  an emulator/device (`/run` + `/verify`), and core flows run the **instrumented E2E smoke** incl.
  an **airplane-mode** leg (P-04). This follows test-driven development: write the failing test
  first, then the code.

## 11 External Data & Backend (SRS §16, §22)

- **Default:** fully offline. The app is useful with no network and no backend.
- **Optional thin backend:** a stateless proxy for market data — mutual-fund NAVs (AMFI), rates
  (RBI), fuel prices — cert-pinned. It **holds no user financial data.** Prices are **never
  scraped on-device.**
- **Degradation (P-04):** every network read is cached with a `fetched-at` timestamp; offline
  shows the last cached value with a **staleness label**. No core path blocks on the network.
- **Consent-gated:** market data, cloud LLM (opt-in; receives only the structured context pack of
  §19.4, never raw transactions), and any future **Account Aggregator** ingestion (§27) sit behind
  explicit, revocable consent.

---

## 12 Greenfield / Migration note

There is **no legacy codebase to migrate** — the repository is greenfield. "Migration" in this
project means only **Room schema migrations** (non-destructive, test-gated per DB version bump,
DB-003). New capabilities (household, business, iOS via KMP) are added on top of the pure-Kotlin
engine layer without rewrites, which is why ARC-002 (Android-free engines) is enforced from day
one.

## 14 Out of Scope (v1) — SRS §1.4, §27

- **Auto-executed money movement** — the app advises and simulates only (P-07). No payments, no
  trades, no auto-transfers.
- **Cloud sync / multi-device server** — the only "sync" is the user-owned local export and the
  E2EE backup. No account server holding financial data.
- **On-device scraping of market data** — market prices come only through the backend proxy
  (§16, §22).
- **Deferred to Epic 13 (design-for, not built in v1):** household & business modes, appliances
  maintenance, full insurance and tax engines, Account Aggregator ingestion, and iOS via KMP.

## Dependency Order (build sequence)

The backlog is topologically ordered by the `Deps` column. The critical path:

1. **Epic 1** foundation (1.1 → Money/Clock/Result → lint → encrypted DB → design system →
   DataStore → app shell) unblocks everything.
2. **Epic 2** (accounts + net worth) → **Epic 3** (transactions) provide the L1 data.
3. **Epic 4** (categorisation/nature) feeds **Epic 5** (dashboard/Safe-to-Spend) and the L3–L5
   engines.
4. **Epic 9** (forecast, health score, orchestrator, guardrail) depends on 3.7 + 4.3 and unblocks
   **Epic 7** (goals/EMF/FOO) and **Epic 10** (advisor/chat).
5. **Epic 6** (wealth) and **Epic 8** (backup) run in parallel once 1.6/2.5 land.
6. **Epic 11** (privacy/security) and **Epic 12** (quality/release) are cross-cutting — start
   early, harden continuously, and gate every merge.
7. **Epic 13** (expansion) is design-for; each item ships an ADR + flagged foundation.
