## Acceptance criteria — how each is met

| Criterion | Evidence |
|---|---|
| Net worth = sum(assets) − sum(liabilities) in `Money` paise; the number comes from the engine, not the LLM (P-03) | `:domain:engines:networth` is pure Kotlin (ARC-002) and the only place the subtraction happens — the repository hands it balances and stores what it returns, the dashboard renders what was stored. `NetWorthPropertyTest` asserts the identity over seeded portfolios, *and* that it equals the plain sum of every signed balance, so the partition can never change the answer it only explains. No `Double` in the module; no division, so nothing to round. |
| A daily snapshot is written via WorkManager on the injected `Clock`, idempotent per day | `NetWorthSnapshotWorker`, daily periodic with `KEEP`. Ids are derived `<profile>:networth:<date>`, so `running twice in a day writes one row, not two`. The day comes from `clock.today()`; nothing here reads the wall clock. Missed days are backfilled from the transactions booked on or before each one — `a backfilled day is computed from the transactions booked by that day` — capped at 90 per run. |
| Golden-file test on a fixed account set; airplane-mode safe | `NetWorthEngineTest.golden - a four-account household` freezes the demo household's figures. Airplane mode: the whole round trip — dashboard, delete, opt-out — driven with the radio off, and nothing on any path touches the network. |
| Golden rules; money/time rules hold | Every amount `Long` paise added through `Money`'s overflow-checked arithmetic (MNY-001); every date ISO in the profile zone (TIM-002); the engine's instant is passed in, never read (TIM-001); provenance carries the engine version so a stored snapshot stays explainable (AI-ARC-006); the three figures are stored together so the total can always be broken down (P-02). |

## What is proven, and what is not

**Proven on a device, and checked by hand.** The dashboard's net worth equals assets − liabilities
over the accounts on screen — arithmetic done manually against the list, three times, after a
delete and after an opt-out. That is the acceptance criterion, verified the way a user would.

**Proven on hardware, not just in a test: the locked-worker path.** logcat shows
`SUCCESS → RETRY → SUCCESS`. The `RETRY` is the app having been force-stopped and the worker firing
before an unlock — exactly the case that would have crashed the process if the repository were
injected eagerly, since the gated `CfoDatabase` provider throws while locked (SEC-002).

**Proven against real SQLite.** The 4 → 5 migration, including that `include_in_networth` arrives
set to `1` on existing rows. A wrong default there would drop every pre-upgrade account out of the
total silently.

**Found by running it, and only by running it.** The dashboard showed the stored snapshot, so
deleting an account left the figure unchanged. Every unit test agreed with the code, because they
all asserted the *stored* value — which was correct. This is the second issue running where the
emulator gate found something no JVM test did (2.5 found a squeezed button), and unlike 2.5's case
this one **could** be turned into a gate, and was.

**Not built, and owned elsewhere.** FR-ACC-005's "1M/6M/1Y/All charts" is issue **6.6** — this issue
produces the series it will read. `liquidity_tier` (§20.2) is untouched; the emergency-fund engine
(§10) is what needs it.

**Still open:** CI has never run — there is no git remote, so every green remains a local green on
one Windows machine.

**Worth knowing for the next issue:** `./gradlew testDebugUnitTest` **does not run the pure-Kotlin
modules** (`:core:model`, `:core:common`, `:domain:engines:*`) — their task is `test`. Running only
the former leaves stale results on disk and can report a failure that no longer exists, which cost
time here. Run `test testDebugUnitTest` together.
