## Acceptance criteria — how each is met

| Criterion | Evidence |
|---|---|
| CRUD for every account type; soft-delete and per-profile scoping | `AccountType` carries FR-ACC-001's eleven with §20.2's stored strings; `every one of FR-ACC-001's account types round-trips` writes and reads all eleven through real SQL, and `the editor offers every one of FR-ACC-001's eleven types` asserts the picker renders them. `deleting is soft — the row survives` reads past the repository to confirm the row is still there (DB-002). `an account created under one profile is invisible to another`. **Archive added beyond the criterion** (FR-ACC-007): a closed account keeps its history and leaves the active list. |
| Balances are `Money` paise; opening + running balance correct (property test) | `AccountBalancePropertyTest` — 10 tests, three fixed seeds, ~2 000 generated transactions across 75 accounts with both signs; asserts `balance == opening + sum(live)` always, plus the edges generation reaches only by luck (no transactions, all soft-deleted, cross-account bleed, odd paise). The stored `current_balance_minor` is deliberately seeded with a garbage value in the fixture so a fallback to it would fail. Money math → **100% coverage** ([ADR-0007](../adr/0007-account-balances-derived-not-stored.md)). |
| The repository is the only DAO toucher; the ViewModel sees domain models only | `AccountRepository` is the sole caller of `AccountDao`; `AccountsViewModel`/`AccountEditorViewModel` hold `com.aicfo.core.model.Account` and import no Room type (ARC-005). The implementation is `internal`, assembled by `RepositoryFactory` (ARC-003). |
| Golden rules; money/time rules hold | Every amount `Long` paise (MNY-001) — the editor parses text once via `MoneyFormatter.parse` and refuses what it cannot represent exactly rather than rounding (P-03); every instant from the injected `Clock` (TIM-001); no network on any path (P-04, verified in airplane mode). The list shows the derived balance *and* the opening balance so the figure is checkable (P-02). |

## What is proven, and what is not

**Proven on a device.** The whole CRUD round trip — onboarding's new fourth step, create, edit,
close, reopen, delete — plus a create in airplane mode. The eleven types render. A liability keeps
its sign end to end.

**Proven against real SQLite.** The 3 → 4 migration carries an existing account across with its
opening balance byte-identical and both new columns NULL. That matters more than the two migrations
before it: those only created tables, so the worst case was a table that did not appear; this one
alters the table a user's accounts live in.

**Proven on the JVM, not on the device:** the balance derivation. `AccountBalancePropertyTest` runs
against real SQLite through Robolectric, unencrypted and in memory. The on-device encrypted database
cannot be queried from `adb` without rooting, so the device evidence for balances is behavioural
(the figures rendered match what was entered), not a row count.

**Not proven, and honestly so: the layout regression test.** The `FlowRow` fix is correct and was
verified on the device by inspecting node bounds before and after. The test added beside it does
**not** reproduce the defect — reverting the fix leaves it green at every screen width tried, with
both `assertIsDisplayed` and an explicit width assertion, because Robolectric's text measurement is a
stub. This is written down rather than glossed over: the project has shipped a vacuous gate before
(audit G-01, `koverVerify` green at 0%), and "the test passes" is not evidence until the test has
been seen to fail. Two other gates in this issue *were* seen to fail, and are logged above.

**Found here, and it had nothing to do with accounts:** `scripts/gen_issue_docs.py` overwrote every
tracker on every run. Fourteen issues' worth of verification logs — the only record that any gate in
this project had ever been executed — existed solely because they happened to be committed. The
generator now refuses to touch a tracker that has recorded progress.

**Still open:** CI has never run — there is no git remote, so every green remains a local green on
one Windows machine.

**Deliberately deferred, with a named owner.** FR-ACC-002 (credit-card limit, statement day) and
FR-ACC-003 (loan principal, rate, EMI, amortisation) need their own tables and belong to issues 3.1
and 3.2. FR-ACC-004 (valuation history) and FR-ACC-005 (net worth) are 2.6's. FR-ACC-006
(reconciliation) is 2.7's, and it is also what will build DB-001's integrity job — the thing that
makes `current_balance_minor` meaningful rather than merely present.

**Worth fixing in a later issue (found here, not fixed):** `:feature:accounts` has no `androidTest`
source set, so its screens are only ever exercised on the JVM. The one defect this issue found on
hardware was a layout one, which is exactly the class Robolectric cannot see.
