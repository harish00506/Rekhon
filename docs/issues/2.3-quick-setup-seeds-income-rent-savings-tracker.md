## What is proven, and what is not

**Proven on the JVM (536 tests, every one of them run):**

- **The budget math, to the paise.** The 50/30/20 split, the metro flex, and the case that matters
  most — a rent past the flex ceiling leaves the needs envelope **visibly short** rather than
  balancing the budget by cancelling the user's savings.
- **Envelopes always total the income exactly**, across 800 seeded awkward amounts, because the
  split goes through `Money.allocate`'s largest-remainder algorithm rather than three separate
  `income * pct / 100` divisions.
- **The savings floor is never breached**, over the same sweep.
- **Nothing is fabricated.** A blank field produces no envelope, no recurring row and no rule
  citation; a skipped step reaches the repository **zero times**; an empty plan writes no row at
  all, not even a profile. Asserted at all three layers independently (engine, ViewModel,
  repository), because one guard is one refactor away from being removed.
- **The write is idempotent.** Ids are derived from profile + kind + period, so re-running
  onboarding updates three envelopes instead of adding three more — asserted against the real row
  count in SQLite, not against a mock.
- **`created_at` survives a re-run** while `updated_at` moves.
- **The stored shape is right in the database, not just in Kotlin:** exact paise in an INTEGER
  column, a signed outflow, a `seed_kind` code rather than an English label, and null
  account/category ids. Checked with raw SQL against the actual columns.
- **The budget period is the profile-zone month** — a setup at 23:30 IST on the 31st files under
  the right month, not UTC's previous day.
- **The summary is on screen**, with the derived figures, the emergency-fund target, the rules that
  fired, and the plain-language sentence for an unaffordable rent (Compose UI tests, incl. dark mode
  and 200% font).
- **Two gates were proven to fail before being trusted** (see below).

**Not proven — the honest gaps:**

1. **Nothing has run on a device.** `adb` is not installed and no AVD exists, unchanged since issue
   2.2. The app has never been launched, so the onboarding → dashboard hand-off, the summary card's
   real rendering, and the airplane-mode leg are all unobserved. A green build does not close this
   issue, and this row is why phases 8 and 9 are `[ ]`.
2. **The 2 → 3 migration has never executed against real SQLite.** `MigrationSafetyTest` proves the
   *structure* on the JVM — that nothing was dropped or retyped, and that both new tables carry
   soft-delete and profile scoping — but `MigrationRoundTripTest.migrate2To3_…` needs a device.
   An existing installation upgrading from v2 is therefore untested end to end.
3. **The encrypted path is untested here too.** `QuickSetupRepositoryTest` runs on unencrypted
   in-memory Room under Robolectric, deliberately: SQLCipher needs a device. What is proven is the
   SQL and the mapping, not that these rows land as ciphertext.
4. **CLAUDE.md §6 is deliberately not satisfied.** The four rulebook thresholds are typed Kotlin
   constants, not rows loaded from `ai/`, because nothing in the app loads `ai/` yet.
   [ADR-0005](../adr/0005-quick-setup-thresholds-deferred-rulebook-loader.md) records the reasoning,
   the drift test that keeps it safe, and the trigger to close it.
5. **Two schemas were designed without their screens.** `budget` and `recurring_rule` belong to
   issues 4.4 and 3.7. [ADR-0004](../adr/0004-quick-setup-persists-budgets-and-recurring-rules.md)
   states exactly what each later issue is expected to add, and every forward-looking foreign key is
   nullable so those additions stay additive under DB-003.
6. **The emergency-fund target is computed, not stored.** It is `needs × runway`, derivable from the
   persisted envelope; issue 7.2 materialises it when the `goal` table exists.

### Gates proven to fail before being trusted

This project has already shipped one gate that passed vacuously (governance audit G-01 — a
`koverVerify` that was green at 0% coverage), so both new gates were made to fail on purpose first:

- **`RulebookDriftTest`** — changing `QuickSetupRules.needsPctMax` from 50 to 51 turned
  `the budget split matches RULE-50-30-20` red, then the value was restored. Without this the
  ADR-0005 deferral would rest on nothing.
- **`koverVerify` on the new engine module** — a temporary uncovered file was added to
  `:domain:engines:quicksetup` to push line coverage under the 85% floor; `koverVerify` FAILED, and
  the file was removed. This confirms the rule is actually wired to the new module rather than
  merely configured somewhere. (A first, smaller probe left coverage at 89.7% and correctly passed —
  worth recording, because that intermediate result is what a careless check would have misread as
  "the gate does not work".)
