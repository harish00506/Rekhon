## Description

Found during the 4.5 (`docs/issues/4.5-budget-alerts-80-100.md`) device-verification pass on
2026-08-15, on the very first cold launch of a fresh install (`CfoTest` AVD, API 34, no PIN ever
configured). Not a regression from 4.5's diff — the racing code is entirely issue 2.2's
(`AppLockGate`, `AppLockViewModel`, `SessionLock`) — but it blocked that session's first attempt at
`/run` and is a first-run crash, so it gets its own ticket rather than a silent fix-in-passing.

**Observed:** on launch, `MainActivity` crashed with:

```text
java.lang.IllegalStateException: The encrypted database was opened while the app was locked
(SEC-002). Feature code must not read financial data before a successful unlock; only the audit
log may, and it injects @AuditDatabase.
    at com.aicfo.app.di.CoreModule.provideDatabase(CoreModule.kt:172)
```

**Root cause — a race between two independent reactions to the same flow emission,
`app/src/main/kotlin/com/aicfo/app/lock/AppLockViewModel.kt`:**

- `uiState` (line ~78) is `combine(appLockStore.observe(), sessionLock.isUnlocked, input) { stored,
  unlocked, current -> toUiState(...) }`. `toUiState`'s status rule (line ~255) is:
  `!stored.enabled -> LockStatus.UNLOCKED` — **independent of the `unlocked` parameter.** The
  moment `appLockStore.observe()` emits a settings row with `enabled = false` (the out-of-the-box
  default for every new install), `AppLockUiState.showsContent` becomes `true` and
  `AppLockGate` (`AppLockGate.kt:56`) composes `content()`.
- Separately, `init {}` (line ~92) launches its own coroutine that does
  `appLockStore.observe().first()` and, if `stored?.enabled == false`, calls `sessionLock.unlock()`
  — the only thing that actually flips `SessionLock.isUnlocked` (and therefore what
  `CoreModule.provideDatabase`'s `check(sessionLock.isUnlocked.value)` reads) to `true`.

These are two separate collectors of the same `appLockStore.observe()` flow with **no
happens-before edge between them**. `combine`'s downstream Compose recomposition can render
`content()` — which immediately requests a Hilt-injected `ViewModel` that provisions
`CfoDatabase` — before the `init` coroutine's `sessionLock.unlock()` call has executed.
`SessionLock`'s own doc comment (`core/crypto/.../SessionLock.kt:25`) states the intended
invariant this violates: *"When the app lock is disabled the gate is opened once at startup by the
same code that reads the setting"* — but it is not the *same* code path, it is a second one racing
the first.

**Reproduction is timing-dependent.** It fired on the first-ever cold launch after install in this
session (slowest DataStore path — creating the settings file for the first time) and did not
reproduce on 3 immediate relaunches afterward (file already exists, both collectors resolve fast
enough that `unlock()` usually wins in practice). This is exactly the shape of bug §21.6 crashes
are meant to catch loudly rather than let slide as a rare flake: it is real and user-facing, just
intermittent.

**Not a defect in the "PIN configured" unlock path.** `unlock(method)` (line ~174) calls
`sessionLock.unlock()` directly and only *then* the `input`/audit updates — `sessionLock.isUnlocked`
is already `true` before `combine` can react to it, so that path has no race.

IDs in code and commits. Binding rules: `CLAUDE.md`.

## Acceptance Criteria

- [ ] `toUiState`'s `!stored.enabled` branch cannot show `content()` before `SessionLock.isUnlocked`
      is actually `true` — either by making `sessionLock.unlock()` happen synchronously on the same
      collection that decides `status`, or by deriving `status` from `sessionLock.isUnlocked`
      directly instead of re-deriving an equivalent condition from `stored.enabled` independently.
- [ ] A test reproduces the race deterministically (e.g. a `TestDispatcher` that lets the `combine`
      emission run before the `init` coroutine is resumed) and goes red without the fix.
- [ ] Repeated cold-start simulation (fresh `AppLockStore` state, lock disabled) never opens
      `content()` while `sessionLock.isUnlocked.value == false`.
- [ ] Golden rules (P-01...P-08) respected; the fix does not weaken SEC-002's fail-secure default —
      `SessionLock` still starts locked (§ its own doc comment) and this fixes a false-negative
      unlock timing, not the lock/unlock semantics themselves.
- [ ] Definition of Done met (`00-issue-workflow.md` steps 9-11; `/pre-merge`).

## Guiding Principles (CLAUDE.md §1)

- **P-08 Deterministic & testable** — the fix must make the ordering deterministic, not just
  reduce the odds of losing the race.
- **SEC-002 / fail-secure** — `SessionLock` must keep starting closed; the fix corrects when it
  opens for the "lock disabled" case, not whether it defaults open.
- **P-02 Show the work** — if the fix changes `toUiState`'s status rule, the doc comment on the
  "status rule" expression (`AppLockViewModel.kt` line ~247) must keep explaining the full
  CHECKING/UNLOCKED/LOCKED contract in one place, per its own stated design goal.

## Workflow Rules — While Solving

### Universal (apply to every issue)

1. Define expected vs actual behaviour with evidence (logs, tests) — the crash stack trace and
   root-cause analysis above are the starting evidence; reproduce it under a controlled
   `TestDispatcher` before changing anything.
2. Form a testable hypothesis, fix, then verify with the original reproduction case (a real cold
   start on a fresh AVD, not just the unit test — this class of bug is exactly what phase-7 device
   runs exist to catch).
3. Smallest correct diff — most likely candidates are (a) having the `init` block set
   `sessionLock.unlock()` synchronously before the `combine` flow is allowed to start collecting,
   or (b) removing the independent `!stored.enabled` branch from `toUiState` and instead unlocking
   `sessionLock` as the single source of truth that `toUiState` reads. Pick whichever keeps
   `SessionLock` as "the one piece of state that says the owner has proved who they are this
   session" (its own doc comment) rather than adding a second path that also claims that.
4. **Respect the boundaries** — this fix stays inside `:app`'s lock package and `:core:crypto`'s
   `SessionLock`; it must not touch `:domain:*` or `:core:model` (ARC-001/002).

### Issue-specific

1. No sleep/delay-based fix. The ordering must be structurally guaranteed (e.g. sequencing within
   one coroutine, or a single source of truth), not "usually wins the race."
