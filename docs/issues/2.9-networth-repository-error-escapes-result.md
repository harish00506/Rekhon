# [2.9] NetWorthRepository's `error(...)` escapes three `Result`-returning APIs

**Status:** Todo
**Epic:** Epic 2 — Onboarding, Security & Accounts
**Priority:** Medium
**Depends on:** 2.6 (this is a bug in that issue's shipped code)
**Assignee:** Harish G
**Labels:** `bug`, `error-handling`

---

## Description

Found while fixing [issue 4.7](4.7-budget-repository-unchecked-engine-casts.md) on 2026-08-16.
`RoomBudgetRepository` had the same *class* of defect — an engine `Result` unwrapped unsafely — and
`NetWorthRepository` turned out to be the precedent that could not be copied, because its answer has
this bug. Filed rather than fixed in 4.7's diff: different file, different feature, different
consumers, and 4.7 was already a four-site change.

**`computeFrom` throws `IllegalStateException` on an engine `Err`**
(`data/repository/src/main/kotlin/com/aicfo/data/repository/NetWorthRepository.kt:354`):

```kotlin
// check, not a silent fallback: the engine fails only on an overflow no real portfolio can
// reach, and §21.6 reserves crashes for programmer errors — which that would be.
return (outcome as? Ok)?.value ?: error("The net-worth engine refused a computed portfolio: $outcome")
```

The reasoning is defensible on its own terms. The problem is where that throw ends up.

**`runCatchingToResult` rethrows `IllegalStateException`** (`core/common/.../AppError.kt:130-131`) —
it is on the deliberate "programmer error, do not swallow" list alongside `IllegalArgumentException`
and `CancellationException`. So `error(...)` escapes **whether or not** it is wrapped, which makes
three of the four call paths lie about their signatures:

| Path | How `computeFrom` is reached | Outcome |
|------|------------------------------|---------|
| `observeCurrent()` `:169` | inside `.map { }` on a `Flow` | **Contained** — propagates as a Flow failure to the consumer's `.catch {}`; `DashboardViewModel` shows its error banner |
| `computeAsOf()` `:188` | `.flatMapToResult(...)` is called **outside** the `runCatchingToResult` at `:190` | **Escapes** a `Result`-returning suspend API |
| `snapshotUpToToday()` `:194` | `snapshotRow` → `computeFrom` `:299`, inside `runCatchingToResult` | **Escapes** — the wrapper rethrows `ISE` |
| `repairStaleHistory()` `:211` | same | **Escapes** — same reason |

The `computeAsOf` case is the clearest, because the wrapping is visibly too narrow:

```kotlin
runCatchingToResult { balancesFor(activeProfileId.first(), asOfIsoDate) }   // wraps only the DB read
    .flatMapToResult(asOfIsoDate)                                          // computeFrom() runs here
```

**Consequence at the consumer.** `NetWorthSnapshotWorker` (`app/.../work/NetWorthSnapshotWorker.kt:81-82`):

```kotlin
if (store.repairStaleHistory() is Err) return Result.retry()
return if (store.snapshotUpToToday() is Err) Result.retry() else Result.success()
```

An escaping `IllegalStateException` is not an `Err`, so it never reaches either branch — it
propagates out of `doWork()`, and `CoroutineWorker` treats an uncaught throw as `Result.failure()`.
The nightly job would stop rather than retry, and **the net-worth series would silently stop
updating** while the dashboard kept rendering the last good snapshot. That is the same shape as the
worker defect 4.7 fixed on the budgets side, arrived at from the opposite direction.

**Why Medium, not High.** The trigger is `NetWorthEngine.compute` returning `Err`, which needs a
`Money` overflow — `Math.addExact` near `Long.MAX_VALUE`, i.e. a portfolio around ±₹92 quadrillion.
No real profile reaches it, and the existing comment says as much. The defect is that three
signatures promise `Result<T, AppError>` and can throw instead, which §21.6 exists to forbid; the
severity is that when it stops being unreachable, the failure mode is a silently dead background job.

## Acceptance Criteria

- [ ] `computeAsOf`, `snapshotUpToToday` and `repairStaleHistory` return `Err` for an engine failure
      rather than throwing — the `Result` in their signature is the only way any of them reports one.
- [ ] The decision at `computeFrom` is made once and stated, as 4.7 did for the budget engine: either
      the throw becomes a carried `AppError` (4.7's `BudgetEngineFailure` is the worked example and
      is `internal` to this module — it would need widening or a sibling), or `computeFrom` returns
      `Result<NetWorthResult, AppError>` and its three callers each decide.
- [ ] `observeCurrent`'s behaviour is stated in its doc comment either way — it is the one path that
      is currently contained, and only by the `Flow` contract rather than by design.
- [ ] A test proves each of the three suspend paths returns `Err` under a failing engine, and that
      `NetWorthSnapshotWorker` retries rather than dying. `RepositoryFactory.netWorth(...)` takes the
      engine as a parameter, so a stub is injectable exactly as `BudgetEngineFailureTest` does it.
- [ ] Whichever shape is chosen matches 4.7's, or the difference is argued in the doc comment —
      two repositories answering the same question differently is what 4.7 set out to stop.

## Notes on approach

4.7's rule does not transfer unchanged, because `NetWorthEngine.compute` has no `Ok(null)` in its
contract — there is no "no net worth", just as there was no "no status". So this is the *load-bearing*
case at every call site, and the question is only how to carry the error out, not whether to degrade.

The cheapest correct change is probably to make `computeFrom` return `Result<NetWorthResult, AppError>`
and let `flatMapToResult` become a real `flatMap` — the `Flow` path then needs an explicit decision
about what `observeCurrent` emits, which is the one genuinely new question here.

**Do not simply widen the `runCatchingToResult` at `:190`.** It would not help: `ISE` is rethrown by
design. That is the trap this issue exists to record.
