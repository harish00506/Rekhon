## The requirement

**FR-TXN-010 (MUST)** — *"Future-dated transactions MUST be supported and excluded from actuals but
included in forecasts."* (SRS §5.3, p.13.)

---

## A third correction to the generated backlog

The pattern from 3.1 (wrong FR id) and 3.3 (a non-existent API and a wrong rounding claim) held for a
third issue running. Both problems are fixed at source in
[`scripts/gen_issue_docs.py`](../../scripts/gen_issue_docs.py) and regenerated.

1. **The criteria cited no requirement id at all** — only "FR-TXN-*". It is **FR-TXN-010**.
2. **"On date rollover they post automatically (WorkManager), idempotently" is not in the SRS.** It
   was authored in the generator. The SRS says only "excluded from actuals but included in
   forecasts", and says nothing about how.

The generator was asked to describe the requirement; it described an implementation. Where these
criteria are *more specific* than the SRS section they cite, they are the author's guess, and the
generator now says so in a comment beside this entry.

**The WorkManager clause was put to the user, who chose to build it** rather than derive posted-ness
from the date alone. [ADR-0010](../adr/0010-future-dated-posting.md) records the shape that satisfies
that choice without inheriting its failure mode: the column and the worker exist, and the *date*
still decides every figure.

## What the tests found that the plan had assumed away

The plan asserted that "excluded from actuals" was already structural, because every balance query
bounds on `booked_on_iso_date <= :asOfIsoDate`. **That was true of net worth and false of account
balances.** `observeWithBalances` and `findWithBalance` — behind the accounts screen, the account
editor and reconciliation — summed every live transaction whenever it happened.

Five tests written before the code failed on the first run, all of them on a balance. The bug was
predicted **by name, in this codebase, eight days earlier**: `balancesForNetWorth`'s doc comment
already said the current-balance query would be "wrong here the moment issue 3.4 lands future-dated
transactions". It was right, and nobody had gone back to the other query.

Had the exclusion been asserted against a *query* rather than against the balance the accounts screen
renders, all five would have passed and the app would have shipped showing two different figures for
the same money.

## Scope decisions (agreed before coding)

| Decision | Why |
|---|---|
| **`posted_at_utc_millis` is a record, not a gate** | Balances derive from the booked date, so a worker deferred by Doze, by a powered-off device, or by the app being locked (SEC-002) cannot make a figure wrong. The stamp is the worker's idempotence key and the marker 3.7 will read. |
| **Two read flows, not one widened window** | `observeRecent()` keeps its `<= today` bound; `observeUpcoming()` covers tomorrow to +90 days. A scheduled row is therefore *never in the list day totals are computed from* — there is no filter for a later screen to forget. |
| **Today or later only** | A back-dated row would change days for which `net_worth_snapshot` already holds a written figure that nothing recomputes. 3.6 owns editing and can revisit it with the recompute it needs. |
| **The date field applies to all three write paths** | One field, passed through `BookingStamps`. Hiding it per direction would have been more code than supporting it — and a scheduled transfer is a plausible thing to want. |
| **`occurredAt` = the start of the booked day** | The list orders by that column, so stamping "now" would sort next month's rent among today's rows. Via `Clock.startOfDay`, which resolves local midnight through the `ZoneId`. |

**Scope boundary — not built:** the forecast engine itself (Epic 6 consumes `observeUpcoming`), the
dashboard's upcoming-obligations card (Epic 5), recurring series (3.7), editing or rescheduling an
existing row (no edit path exists anywhere; 3.6), notifications on post.

## What static analysis forced, and why each was fair

Five, and not one was noise:

- **`LocalDate.EPOCH` is API 34; this app's minSdk is 26.** Caught by `lintDebug` and by nothing
  else — every unit test runs on the JVM, where the constant exists, so this compiled, passed 890
  tests and would have crashed on a real phone. Now `LocalDate.ofEpochDay(0)`.
- **`AddTransactionViewModel.kt` hit the eleven-function ceiling** the moment the schedule reducer
  was added. `applySchedule` moved to `ScheduleField.kt` — a deviation from where 3.3 put
  `applySplit`, and the more honest shape: a change to what the date button offers and a change to
  what picking a date does are the same change.
- **`TransactionsContent` passed 40 lines** → `LazyListScope.scheduledSection`. Everything extracted
  renders only for a user who has scheduled something, which is almost nobody.
- **`AddTransactionViewModelTest` passed the 600-line class limit** → `AddTransactionScheduleTest`.
  Fair: future dating is a distinct claim from the tap budget that file exists to pin.
- Two formatting fixes (import order, a multiline expression).

## Notes for later issues

- **Issue 9.2 (cash-flow forecast) is the first real consumer of `observeUpcoming`.** It is the
  "included in forecasts" half of FR-TXN-010, and this issue ships only the read. The window is
  `UPCOMING_WINDOW_DAYS = 90`; raise it there if the forecast horizon needs more.
- **Issue 3.7 (recurring detection) is the first real consumer of `posted_at_utc_millis`.** Until
  then the column is a record nothing reads — deliberately, per ADR-0010.
- **Never gate an amount on a background job.** The general form of this issue's central decision,
  and worth applying to every worker added after it.
- **A doc comment that predicts a bug does not prevent it.** `balancesForNetWorth` named this exact
  failure eight days before it could happen, in the file containing the query that had it. Assert
  the *user-visible figure*, not the query you happen to be thinking about.
- **`gen_issue_docs.py` still blanks completed issue docs.** Four this time. `git diff docs/issues/`
  after every run remains mandatory; most of the noise is CRLF-only and only a handful are real.
- **The emulator's date can be moved** (`adb root`, `settings put global auto_time 0`,
  `adb shell date MMDDhhmmYYYY.ss`), which is how a day-rollover feature gets verified rather than
  argued about. Restore `auto_time 1` afterwards.
