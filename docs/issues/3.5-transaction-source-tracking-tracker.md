## The requirement

**FR-TXN-009 (MUST)** — *"Every transaction MUST record its source: manual, ocr, sms, import,
recurring-auto."* (SRS §5.3, p.13.) Plus **P-02**, which is what makes recording it insufficient on
its own.

---

## The row this issue exists for

A reconciliation adjustment (FR-ACC-006) has `note` deliberately set to null, so before this it
rendered as:

```
Uncategorised                        -Rs 500.00
```

Nothing said the *app* had posted it to close a gap against a statement the user typed.
`TransactionEntity.source`'s own doc comment already stated the fix — "on that row the source **is**
the rule that fired" — and issue 3.1's tracker deferred the work here by name: "3.5 owns surfacing
and filtering; 3.1 only made them parseable". A verdict with no visible reason is what P-02 forbids.

It now reads **"Balance adjustment"**, verified on the emulator against a real posted adjustment.

## A fourth correction to the generated backlog

3.1 had the wrong FR id, 3.3 cited a non-existent API, 3.4 invented a WorkManager clause. This one
had three problems, all fixed at source in
[`scripts/gen_issue_docs.py`](../../scripts/gen_issue_docs.py) and regenerated.

1. **The FR id was `AI-ARC-003`.** That rule governs *engine result* provenance — `engineId`,
   `engineVersion`, `inputWindow`, `computedAt`, `confidence`, `evidence` — and has nothing to say
   about a transaction row. **No engine writes a transaction**, so the criterion's "creating
   engine/version where applicable" applied to nothing. The requirement is **FR-TXN-009**. (§18,
   also cited, is the OCR workflow: relevant to where the value `ocr` comes from, not to this.)
   **No `engine_id` column was added.** When 3.7's recurring rules start writing rows, the *rule* id
   is what will belong there, and that is 3.7's to design.
2. **"shown in the detail view"** — there was no detail view, and this issue deliberately did not
   add a route for one.
3. **"a default is backfilled for manual entries"** — **nothing to backfill.** `source` has been
   `TEXT NOT NULL` since schema v1 and every write path sets it explicitly; a row without one cannot
   be constructed. Writing a migration would have been writing a no-op. The honest substitute is the
   assertion `every write path stamps a source, so there is nothing to backfill`, which drives all
   four write paths and checks every stored value still parses.

**The pattern is now four for four.** Where these generated criteria are *more specific* than the
SRS section they cite, they are the generator author's guess at an implementation.

## Scope decisions (agreed before coding)

| Decision | Why |
|---|---|
| **Row label + detail bottom sheet, no route** | The label answers "what is this?" where the user already is; the sheet answers "tell me everything" with no `CfoRoute`, no back stack and no navigation test. 3.6 owns editing and will want a real screen — building a third of one now is how 3.6 gets built badly, which this codebase has recorded twice. |
| **`MANUAL` renders no row label** | It is the default and the overwhelming majority. Tagging every hand-typed row "Manual" would bury the few labels carrying information. **The sheet spells it out anyway** — in a field list a blank reads as missing data, not as the default. |
| **The chip row needs ≥ 2 distinct sources** | Verified on the emulator: a freshly-onboarded real profile shows **no chips and no labels at all**. The common case pays nothing for this feature. |
| **Filtering in the ViewModel, not in SQL** | It applies to rows `observeRecent`/`observeUpcoming` already emit, so no DAO or repository change — nothing that can conflict with the real filter mechanism 3.6 builds. FR-TXN-007's filter list (date, account, category, type, amount) does **not** include source, so this filter is genuinely 3.5's. |
| **Filter before grouping** | `TransactionDay.total` folds the rows under it, so day totals recompute to the filtered rows for free. Filtering afterwards would leave every header stating a total for transactions no longer beneath it. |
| **`availableSources` from the *unfiltered* rows** | Derived from what is on screen, choosing a chip would delete every other chip and strand the user with no way back to "All". |
| **`RECURRING_AUTO` added now, stored as `recurring_auto`** | FR-TXN-009 names it; underscore matches `transfer_out`/`transfer_in`. Nothing writes it until 3.7 — the value exists so a row from a newer build renders rather than being dropped by the mapper, the exact failure omitting `DEMO` caused in 3.1. |

**Scope boundary — not built:** a transaction detail *route* (3.6, with editing), search and
FR-TXN-007's other five filters (3.6), bulk edit (FR-TXN-008), the writers for `OCR` (3.8), `SMS`
(3.9), `IMPORT` (5.4) and `RECURRING_AUTO` (3.7), and any engine-provenance column.

## What the tests caught

**Two failures, both real, both from tests written before the code.**

- **A filtered-to-nothing list rendered *both* empty messages.** `isEmpty` had three clauses —
  not loading, no error, no rows — and a filter matching nothing satisfies all three. So the screen
  said "No transactions yet. Tap + to add your first one." to a user who has plenty and had merely
  narrowed the view. `sourceFilter == null` is now the fourth clause. **This is the same argument
  the class had already made three times** (loading is not empty; a failed read is not empty; a
  scheduled-only profile is not empty) — the fourth instance still had to be found by a test.
- **`setContent` called twice in one test.** Exactly the mistake issue 3.3 recorded, made again.
  Split into two tests.

## Notes for later issues

- **Issue 3.6 inherits a filter it did not design.** The source chip row filters in the ViewModel
  over an already-loaded window. When 3.6 adds paging and FR-TXN-007's five filters, that stops
  being viable — filtering a page is not filtering a table — and the source filter should move into
  the query with the rest. It was kept out of SQL deliberately so that move is 3.6's to make.
- **Issue 3.6 also inherits the detail sheet.** It is read-only and deliberately routeless. When
  editing lands, a real `CfoRoute.TransactionDetail` is the right answer and this sheet should be
  replaced rather than grown.
- **Issue 3.7 is the first writer of `RECURRING_AUTO`**, and the first place an engine or rule id
  on a transaction would make sense — which is what the criteria's AI-ARC-003 reference was
  reaching for a whole issue early.
- **`isEmpty` has now grown a clause four times** (loading, error, scheduled-only, filtered). Any
  future state that empties the two lists without emptying the profile must add a fifth. The general
  form: **"nothing on screen" and "nothing exists" are different claims**, and only the second one
  may say so to the user.
- **`gen_issue_docs.py` blanked five completed docs this time**, up from four. `git diff --stat
  docs/issues/` after every run remains mandatory; the ~150 files `git status` reports are almost
  all CRLF-only noise.
