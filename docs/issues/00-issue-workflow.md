# Issue Workflow — AI Personal CFO (Android)

When working on any task, issue, or epic:

1. **Read** this file (master workflow + guiding principles §A below) and **`CLAUDE.md`**
   (the binding project rules). They override feature requests.
2. **Open** `docs/issues/<id>-<slug>.md` — load its **Skill Rules** table and read the listed
   skill/spec files. (Template: [`_ISSUE_TEMPLATE.md`](_ISSUE_TEMPLATE.md).) The full epic/issue
   backlog is the design spec
   [`../superpowers/specs/2026-07-17-ai-personal-cfo-design.md`](../superpowers/specs/2026-07-17-ai-personal-cfo-design.md)
   §13 + [`../superpowers/specs/2026-07-17-issues.csv`](../superpowers/specs/2026-07-17-issues.csv)
   (13 epics, 85 issues); the per-issue files are generated by
   [`../../scripts/gen_issue_docs.py`](../../scripts/gen_issue_docs.py) — edit the CSV/generator
   source, not individual files, when adding or renaming issues.
3. **Read the spec section cited in the issue** — `docs/init/AI_Personal_CFO_SRS_v1.7.pdf`.
   Capture the exact **requirement IDs** (`FR-…`, `AI-ARC-…`, `RULE-…`, `MNY-…`, `TIM-…`) and
   quote the acceptance criteria back. Also read any `ai/` file the behaviour touches
   (`ai/README.md` is the map).
4. **Check dependencies** — stop if blockers exist (list them in the issue and tracker).
5. **Respect the boundaries** (the analog of "don't touch the core engine"):
   - Dependency direction is one-way: **`feature → domain → data/core`** (ARC-001). Feature
     modules never depend on each other.
   - **Engines are pure Kotlin** (no Android imports, ARC-002); **repositories are the only
     classes that touch DAOs or network** (ARC-005).
   - **Never hardcode a financial number** — thresholds live as versioned rows in
     `ai/rules/rules-kb.json` (§29). Use the `add-rulebook-rule` skill.
   - **Numbers come from math, words from AI (P-03)** — the LLM never computes; it verbalises
     engine output, gated by `ai/chat/guardrail.md` (AI-ARC-004).
6. **Scientific method**: observe → reproduce → hypothesize → isolate → fix → verify.
   Use the `debugging-and-error-recovery` skill for root-cause work — no guess-patching.
7. **Minimal scope** — apply **`/ponytail`** (laziest solution that actually works: YAGNI,
   stdlib/first-party before deps, one line before fifty); match existing conventions.
   **Privacy & isolation on every path**: per-profile/household scoping, soft-delete
   (`deleted_at`), provenance on every engine result (AI-ARC-003), no new off-device data
   flow without explicit, revocable consent (P-01).
8. **Branch while working** (off `dev`): `feature/<id-with-dashes>-<short-slug>`.
9. **Run + verify (required before Done)** — the app must be **run and observed working**; a
   green build or green `./gradlew test` does **not** close an issue.
   - **Static analysis:** `./gradlew ktlintCheck detekt lintDebug` — no new warnings (§21.6).
   - **Unit + coverage:** `./gradlew testDebugUnitTest koverVerify` — **engine ≥ 85%, money
     math 100%** (§21.5).
   - **Screenshots (if UI changed):** `./gradlew verifyPaparazziDebug`.
   - **AI data (if `ai/**` changed):** confirm JSON/YAML parse and IDs/versions were bumped
     (`python -c "import json,glob;[json.load(open(f,encoding='utf-8')) for f in glob.glob('ai/**/*.json',recursive=True)]"`).
   - **Run it (the real gate):** build, install on an emulator/device, and **exercise the
     changed behaviour against the running app** — use the `/run` skill to launch and the
     `/verify` skill to drive it. Confirm the affected screen/flow actually works
     (e.g. add-txn ≤ 3 taps, dashboard renders, forecast updates, purchase-advisor verdict
     shows its trace). Where the change is core, run the **instrumented E2E smoke**
     (`./gradlew connectedDebugAndroidTest`): onboard → add data → verify dashboard/forecast →
     export/import round-trip → **airplane-mode pass** (P-04, §21.5).
   - `SKIP — <reason>` only when no emulator/device is genuinely available; never skip for
     convenience. If the issue touches the thin backend (§22), run it locally too and confirm
     the app still passes **with the backend absent** (P-04).
   - Log every command + result in the tracker **Verification Log** (step 11).
10. **When task is complete**: open a PR from your `feature/<id>-<slug>` branch into **`dev`**
    (the integration branch) — **never push straight to `main`/`stage`** (both protected,
    PR-only, §21.6). In the PR, update the tracker + any `ENGINE.md`/ADR docs and bump
    `VERSION` + `CHANGELOG.md` (see Versioning below). After it merges to `dev`, **promote by PR**:
    `dev → stage` for live testing, then `stage → main` for release. Do not leave finished work
    only on a feature branch.
11. **Tracker + Verification Log (required when Done)** — create/update
    `docs/issues/<id>-<slug>-tracker.md` from [`_TRACKER_TEMPLATE.md`](_TRACKER_TEMPLATE.md).
    Must include:
    - **Status Summary** (progress, last verified timestamp **UTC+5:30**, branch, VERSION).
    - **Phase Checklist** (`[x]` / `[ ]` with one-line verification per row).
    - **Verification Log** table:

      | Date & time (UTC+5:30) | Phase | Command | Result |

      Append a row for every verify step (lint, unit, Paparazzi, emulator run, E2E, git push).
      Use `OK`, `SKIP — <reason>`, or `FAIL — <reason>`. Link the tracker from the issue file.
12. **Do not commit or push** unless the user explicitly requests (except step 10 when they ask
    to finish and ship).

## A. Guiding principles (from `CLAUDE.md` §1 / SRS §1.3 — binding)

- **P-01 Privacy first** · **P-03 Numbers from math, words from AI** · **P-04 Offline-first**
  · **P-07 Advice, never orders** · **P-08 Deterministic & testable** · **P-02 Show the work**
  · **P-06 India-native** (INR paise, lakh/crore, FD/RD/PPF/EPF/NPS/ELSS, RBI/AMFI data).
- **Money & time (§21.4, review-blocking):** `Money` = `Long` paise end-to-end, rates in bps —
  **no `Double`/`Float` on money**; injected `Clock`, **never `System.currentTimeMillis()` in
  domain**. Run the `money-time-audit` skill on every diff that touches amounts or dates.
- Rule of thumb: **prefer the boring, testable, explainable option. Cleverness is a cost.**

## Skills & commands (use these)

Drive issues through these Claude Code skills / slash commands:

- **`spec-driven-development`** — for feature work grounded in the SRS: write/refresh the
  feature spec before coding. Then use **`/new-feature <REQ-ID>`** (this project's command) to
  run the spec-driven flow: find the spec → place it in the architecture → plan & confirm →
  tests first → implement → document → `/pre-merge`.
- **`planning-and-task-breakdown`** (or the **Plan** agent) — for any non-trivial issue, plan
  before coding: critical files, approach, trade-offs, task order. Run it **after** the
  dependency check (step 4) and **before** the fix (step 6).
- **`new-engine`** — scaffold a new `:domain:engines:*` module correctly (one interface +
  result types, provenance, Hilt, `ENGINE.md`, golden-file/property/determinism tests).
- **`add-rulebook-rule`** — add/change any financial threshold as a versioned data row in
  `ai/rules/` (never hardcoded), cited by ID, with an evaluator test.
- **`money-time-audit`** — scan the diff for the two bug factories before merge.
- **`test-driven-development`** — write the failing test from the acceptance criteria first,
  then implement to green (step 6, Testing below).
- **`incremental-implementation`** — land in small reviewable slices; feature-flag incomplete
  work (no long-lived branches).
- **`debugging-and-error-recovery`** — the scientific-method engine for step 6.
- **`source-driven-development`** — ground framework/library use in official docs (Compose,
  Room, Hilt, ML Kit) rather than outdated patterns.
- **`/ponytail`** — keep every solution the laziest that actually works. Enforces step 7.
- **`/run`** + **`/verify`** — launch the app and drive the changed behaviour (step 9's real gate).
- **`/pre-merge`** — the Definition-of-Done gate (§4.2); run before shipping (step 10).
- **`code-review`** and **`security-review`** — review the diff before merge; security review is
  mandatory for anything touching crypto, keys, SMS parsing, backup, or consent (§23, SEC-*).
- **`/loop`** — for recurring/iterative runs: working a backlog of issues, or polling a build /
  emulator check until green. Omit the interval to self-pace.

## Testing & Coverage (required before Done)

Applies to every function, method, engine, or composable you add or change:

1. **Doc + test per function.** Each new/modified function ships with **(a)** a doc comment
   stating *why / what / result / changelog / inputs / outputs* (global rule + §21.6) and
   **(b)** at least one test covering the normal case plus edge / boundary / empty / error
   paths. No function lands untested — if it is too trivial to test, say so in one line in the
   tracker rather than skipping silently.
2. **Green gate — all touched suites pass.** Before Done, the **full** suite for every area the
   change touches must pass, not just the new tests. A failing or skipped-for-convenience suite
   blocks Done. Passing suites are necessary but **not sufficient** — the running app must also
   be verified on an emulator per step 9.
   - **Unit (domain/data/viewmodel):** `./gradlew testDebugUnitTest` (JUnit5, Turbine, MockK,
     Robolectric). Coverage gate: `./gradlew koverVerify` (engine ≥ 85%, money math 100%).
   - **Screenshot:** `./gradlew verifyPaparazziDebug` for design-system components in
     light/dark/200% font.
   - **UI / user-flow (the Playwright analog):** Compose UI tests plus the **instrumented E2E
     smoke** — `./gradlew connectedDebugAndroidTest` on an emulator/device for any screen,
     navigation, or user-flow behaviour. If no device is attached, start one
     (`emulator -avd <name>`) or log `SKIP — no device`.
   - **AI evaluation (if the change affects a model/classifier/forecast):** run the frozen
     labelled datasets — categorisation ≥ 92%, receipts ≥ 95%, forecast backtests. Regression
     thresholds **block merges** (§21.5).
3. **Log every run.** Record each suite run (command + `OK`/`FAIL` + pass count) in the issue
   **Verification Log**, the same way emulator/run steps are logged (step 11). `M skipped` must
   name *why* (e.g. `2 skipped — no attached device`), never skipped to go green.

## Versioning & Changelog (SemVer)

Single source of truth: **`VERSION`** (repo root, one line, e.g. `0.1.0`) and
**`CHANGELOG.md`** (repo root, [Keep a Changelog](https://keepachangelog.com) format). Keep
`app/build.gradle.kts` `versionName` equal to `VERSION`; bump `versionCode` monotonically (do
not force any other module's version to match). Epics map to the SRS roadmap & milestones (§26)
and requirement traceability (§28) — cite requirement IDs in every changelog entry.

1. **Starting a new Epic → minor bump `+0.1.0`** (e.g. `0.2.7 → 0.3.0`, patch resets to `0`).
   Add a new `## [x.y.0] — Epic N: <name>` heading in `CHANGELOG.md` **before** the epic's
   first issue.
2. **Finishing an epic sub-task (issue) → patch bump `+0.0.1`** (e.g. `0.3.0 → 0.3.1`). At
   Done/ship time, bump `VERSION`, `versionName`/`versionCode`, and add an entry under the
   current epic heading:

   ```
   ### [x.y.z] — Issue <id>: <title>  (YYYY-MM-DD)
   - **Implemented / updated:** <one or two lines on the behaviour delivered> (<REQ-IDs>)
   - **Tests:** N passed, M skipped  (+ emulator E2E / airplane-mode / migration round-trip if relevant)
   ```

   `M skipped` must name *why* anything skipped, never skipped to go green.
3. **When:** the bump + changelog entry are part of the ship step (step 10) — same commit/push
   as the tracker update. Mention the new version in the ship summary. The
   `changelog-automation` and `git-workflow-and-versioning` skills help here.

## External integrations — prefer the first-party / pinned library

The stack is **pinned** in SRS §21.3 — use the pinned choice; do not hand-roll or swap it
without an ADR:

- **Network** → Retrofit + OkHttp + kotlinx.serialization (certificate-pinned to our own
  backend). Market NAVs/prices come **through our backend proxy** (AMFI, RBI, fuel), never
  scraped on-device (§16, §22).
- **Crypto** → **Google Tink / platform Keystore only. No hand-rolled crypto — review-blocking
  (SEC-003).**
- **OCR** → ML Kit Text Recognition v2 (on-device). **On-device LLM** → AICore / MediaPipe
  (Gemma-class) behind the `LlmEngine` interface; cloud LLM is opt-in and receives only the
  structured context pack (§19.4), never raw transactions.
- **Persistence** → Room + SQLCipher; **Preferences** → Proto DataStore (SharedPreferences
  banned); **Background** → WorkManager; **Biometrics** → BiometricPrompt (class 3).
- If a required library is genuinely synchronous, call it off the main thread via the injected
  `DispatcherProvider` (IO) — never block the UI. New third-party deps are scanned in CI (OSV,
  SEC-007) and justified in the issue.
