# [4.7] BudgetRepository turns an engine `Err` into a `ClassCastException`

**Status:** Done — all four sites fixed, tested against a failing engine, device-verified.
**Epic:** Epic 4 — Categorisation & Budgets
**Priority:** Medium
**Depends on:** 4.4 (this is a bug in that issue's shipped pattern; 4.5 and 4.6 copied it)
**Assignee:** Harish G
**Labels:** `bug`, `error-handling`

---

## Description

Found during the code review of issue 5.1 on 2026-08-16 (`/code-review` over
`404f50d..HEAD`). Not a regression from 5.1's diff, and not solely 4.6's: the pattern was
established by 4.4 and copied twice since, which is why it is filed rather than fixed in passing —
a one-site fix would leave three identical hazards behind and make the file inconsistent about how
engine failures are handled.

**`RoomBudgetRepository` unwraps every engine result with an unchecked cast**, at four sites in
`data/repository/src/main/kotlin/com/aicfo/data/repository/BudgetRepository.kt`:

| Line | Call | Shipped in |
|------|------|-----------|
| ~567 | `status = (status as Ok).value` | 4.4 |
| ~599 | `((alert as Ok).value)?.let { ... }` | 4.5 |
| ~685 | `return (review as Ok).value` | 4.6 |
| ~756 | `((suggestion as Ok).value)?.let { ... }` | 4.4 |

Every one of `BudgetEngine.suggest`/`status`/`alert`/`review` is implemented as
`runCatchingToResult { ... }` (`DefaultBudgetEngine.kt:49, 68, 84, 90`), so each **genuinely can**
return `Err`. When that happens the cast throws `ClassCastException` from inside a `combine`
transform, which is exactly the "no exceptions across layer boundaries" rule (§21.6) that the
`Result` return type exists to enforce.

> **Correction (2026-08-16, while fixing).** This paragraph originally listed "a `MonthlySpend`
> precondition, or any future `require` inside the engine" alongside the overflow. That is wrong:
> `runCatchingToResult` **rethrows** `IllegalStateException` and `IllegalArgumentException`
> (`AppError.kt:128-133`), so an engine `require`/`check` crashes rather than becoming `Err`. And
> `:domain:engines:budget` is pure Kotlin with no I/O and no crypto, which rules out `Storage`,
> `Crypto`, `Validation` and `NotFound` too. **The whole reachable error set is
> `Unexpected(<class name>)`** — realistically `ArithmeticException` from `Math.addExact` on an
> amount near `Long.MAX_VALUE`. The defect is real either way; its blast radius is narrower than
> first written, and that rethrow list turned out to constrain the fix (see below).

**Why it is Medium and not High:** the inputs this repository assembles are validated before the
engine sees them, so no *currently reachable* input is known to produce an `Err`. The defect is that
nothing guarantees that, and the failure mode when it stops being true is a crash or a silently
blank card rather than the `AppError` the signature promises.

**Observed consequences, in order of severity:**

1. **Was a crash, until 2026-08-16.** `acceptReviewProposal` and `acceptSuggestion` called
   `observeReview()`/`observeSuggestions().first()` — both of which run the casts — with no
   `runCatchingToResult` guard, so the throw escaped a `Result`-returning API into
   `viewModelScope.launch` in `BudgetsViewModel`, where nothing catches it. **This half is already
   fixed** (same review pass): both methods now wrap their read in
   `withContext(dispatchers.io) { runCatchingToResult { ... }.flatten() }`. The cast itself is what
   remains.
2. **A silently vanishing card.** With the guard in place, an engine `Err` on the `observeReview`
   path now surfaces as `AppError.Unexpected("ClassCastException")` — or, on the Flow path, is
   swallowed by `BudgetsViewModel.observeReview`'s `.catch`, which clears the review to `null`. The
   user sees the month-end review simply not appear, with no error and nothing in the log to say
   why.
3. **The error's identity is lost.** Even where it is caught, `Unexpected("ClassCastException")` is
   reported instead of the engine's own `AppError`, so the audit trail names the symptom rather than
   the cause.
4. **A worker that retries forever, silently.** `BudgetAlertWorker` maps `pendingAlerts()`'s `Err` to
   `Result.retry()`. A cast failure there is deterministic given the same rows, so the job retried
   daily for the rest of the month, notifying nothing and recording nothing.

## Acceptance Criteria

> **The original four ACs were rewritten on 2026-08-16, during the fix.** As first written they were
> unsatisfiable by any sane design: AC1 demanded the sites "propagate the engine's own `AppError`
> instead of throwing" when three of them have nowhere to propagate it *to* and the fourth has
> nothing to do *but* throw; AC2 demanded "not silence" when silence is the correct outcome for
> three of them. They were written before the `runCatchingToResult` rethrow list and
> `BudgetEngine`'s own `Ok(null)` contract were understood. Amended rather than stretched.

- [x] No unchecked `as Ok` cast remains in `RoomBudgetRepository`. Each site handles the `Err`
      explicitly, per the rule `BudgetEngine`'s own contract sets: where the engine documents
      `Ok(null)` as a legitimate answer (`suggest`, `alert`, `review`), a failure collapses into that
      same absence; where it does not (`status`), the failure terminates the stream carrying the
      engine's `AppError`, and every suspend path that reads it converts that back to `Err`.
- [x] A test proves each of the four paths behaves as documented under an engine `Err` — the three
      optional paths degrade to absence **while the figures beside them survive**, and the `status`
      path surfaces the engine's own `AppError` rather than a `ClassCastException`, including through
      the suspend reads that must still return `Err`. `BudgetEngineFailureTest`, nine cases, using a
      stub injected through `RepositoryFactory.budgets`.
- [x] Every read whose failure behaviour a consumer can observe says so in its doc comment:
      `observeBudgets`, `observeSuggestions`, `observeAlerts`, `alertFor` (public since 5.1, and
      synchronous — a caller meets the degradation with no Flow in between), `observeReview` and
      `pendingAlerts` (whose contract changes).
- [x] One rule, stated in `BudgetRepository`'s own interface doc comment so a reader can find it,
      applied to all four sites.

## What was decided, and why

The rule is **inherited from `BudgetEngine`'s own interface rather than invented here**, which is
what makes it checkable: `suggest`, `alert` and `review` each document `Ok(null)` as a legitimate
answer (`BudgetEngine.kt:35, 58, 78`) and `status` (`:48`) does not, because there is no such thing
as "no status". A failure therefore has a lane to land in at three sites and none at the fourth.

An earlier framing — "advisory results degrade, load-bearing ones surface" — was dropped: it
produces the same four edits but is a judgement a reviewer cannot check, and the next engine call
added to this file would have been argued into whichever bucket was cheaper.

**`Flow<Result<…>>` was considered and not taken.** No repository in `:data:repository` carries an
error inside a stream (the pattern exists only in `:core:datastore`, and `DemoModeRepository`
unwraps it immediately at the boundary), so adopting it here would rewrite the contract every
`.catch {}` consumer is written against, in two ViewModels, for a failure that is currently
unreachable. Recorded here as the option not taken.

**`error(...)` was considered and rejected** despite `NetWorthRepository.computeFrom:354` doing
exactly that for a structurally identical non-nullable engine call. `runCatchingToResult` rethrows
`IllegalStateException`, so an `error()` at the `status` site would escape `pendingAlerts`,
`acceptSuggestion` and `acceptReviewProposal` into `viewModelScope` and `CoroutineWorker` — exactly
the §21.6 hole closed on 2026-08-16. `BudgetEngineFailure` extends plain `Exception` for that
reason, and is `internal` to `:data:repository` so it cannot become an app-wide "throw an `AppError`
instead of returning one" hatch beside the `Result` type that exists to prevent one.

**On the "structured log at the drop site" the original note asked for: not satisfiable.** There is
no structured logger anywhere in this codebase (CLAUDE.md §5 aspires to one; none was built),
`:data:repository` depends on no logging library, and `AuditLogRepository` is closed to non-security
events by construction — a closed `AuditEvent` enum with no free-text column. Adding a logging
dependency needs a `DECISIONS.md` row and is a larger change than this bug warrants. The three drop
sites are marked in their doc comments instead; `Result.onErr` is already documented in
`:core:common` as "the logging seam for errors", and these three become its first callers the day
one exists.

## Follow-up filed separately

**[Issue 2.9](2.9-networth-repository-error-escapes-result.md)** — `NetWorthRepository.computeFrom:354`'s
`error(...)` escapes **three** `Result`-returning APIs, not the one first suspected: `computeAsOf`
(whose `runCatchingToResult` is wrapped too narrowly to cover it), plus `snapshotUpToToday` and
`repairStaleHistory` (where it *is* wrapped, and escapes anyway because `runCatchingToResult`
rethrows `IllegalStateException` by design). `NetWorthSnapshotWorker` maps only `Err` to a retry, so
the escape would kill the nightly job outright and stop the net-worth series silently. Verified end
to end on 2026-08-16 and filed; deliberately not widened into this diff.

## Verification

```text
./gradlew ktlintCheck detekt lintDebug     # OK, clean first run
./gradlew unitTests koverVerify            # OK
```

- **The new tests were confirmed to catch the bug**, not merely to pass beside it: all four casts
  were reverted and `BudgetEngineFailureTest` went **8 of 9 red**, each with a real
  `ClassCastException` at the reverted site (`alertFor`, `reviewFor`, `suggestionFor`). The ninth —
  "a refused status reaches a suspend reader as `Err`" — passes either way by design: it guards the
  containment property against a future `error(...)`, and would only fail if someone reintroduced a
  rethrown exception type.
- **Device-verified** on the `CfoTest` AVD with airplane mode on (`airplane_mode_on` = 1): dashboard
  and budgets screens render exactly as before against the real engine, with real profile data. This
  fix must be invisible when nothing is failing, and it is.
