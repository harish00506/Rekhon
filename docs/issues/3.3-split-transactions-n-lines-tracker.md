## The requirement

**FR-TXN-004 (MUST)** — *"Split transactions MUST allow N lines with independent categories; lines
MUST sum exactly to the parent amount (validated, no rounding drift)."*

---

## Two corrections to the generated backlog

Both fixed at source in [`scripts/gen_issue_docs.py`](../../scripts/gen_issue_docs.py) and
regenerated — the same class of stale-generated-doc problem as 3.1's wrong FR-ID.

1. **`Money.splitExact` does not exist.** The real API is `split(intoParts)` and `allocate(weights)`.
2. **"The remainder is distributed via HALF_EVEN" is wrong, and not just about the code.** HALF_EVEN
   lives only in `Money.percentOf`; `allocate` uses **largest-remainder (Hamilton)**. More
   importantly HALF_EVEN *cannot* satisfy the requirement: rounding three ₹333.333… shares
   half-to-even gives ₹999.99 — precisely the "rounding drift" FR-TXN-004 forbids. **The SRS never
   says HALF_EVEN here**; it says "no rounding drift", which only a remainder-distribution rule
   delivers. Seen on the emulator as 333.34 / 333.33 / 333.33.

A third note rather than a correction: **"lines sum exactly to the parent" is already property-tested
at the `Money` level** (`MoneySplitPropertyTest`). This issue's property test therefore asserts the
sum **on rows read back out of SQLite**, which is the part that was unproven.

## Scope decisions (agreed before coding)

| Decision | Why |
|---|---|
| **A `transaction_splits` child table** | The parent holds the money and moves the balance; lines only attribute it, so **no balance query changed and no balance code was written**. §20.1 names the table, and unlike the `transfers` table ADR-0008 rejected, it holds real facts. |
| **Lines carry an optional `category_id`** | Consistent with 3.1 and 3.2. A real profile has none until issue 4.1; demo has twelve. |
| **An opt-in "Split into lines" toggle on the add screen** | FR-TXN-002's two-tap expense is pinned by a test, so a split control that was always expanded would spend a tap the budget does not have. Orthogonal to Expense/Income/Transfer — a split expense is still an expense. |
| **Refusal, never adjustment** | Lines one paise out are rejected. An app that quietly moves a user's figure to make a form balance is worse than one that says no. |

**Scope boundary — not built:** splitting an already-saved transaction (no edit path exists; 3.6 owns
bulk edit), future dating (3.4), a source/type filter (3.5), search/filters (3.6), the category
taxonomy (4.1), Need/Want/Invest per line (4.3).

## Structural changes detekt forced, and why they were fair

The plan predicted the 40-line limit would bite. It bit four times, and each was a real signal:

- **`SplitEditor.kt`** — `AddTransactionScreen.kt` passed the eleven-function ceiling. The seam is
  genuine: everything extracted is one optional mode that renders nothing unless asked for.
- **`SplitDrafts.kt`** — likewise for `TransactionRepository.kt`. Everything moved is about one
  amount divided across categories, and none of it touches a balance.
- **`SplitEvent`**, a nested sealed interface — six new events flattened into `AddTransactionEvent`
  pushed `onEvent` past its complexity ceiling. Grouping them says what is true: the split editor is
  its own mode, with its own reducer (`applySplit`).
- **`SplitLineCategories`** — split from `SplitLineRow`, and it is the part that vanishes entirely
  for a real profile.

## Notes for later issues

- **Issue 4.4 (budgets vs actuals) is the first real consumer.** It must sum **split lines** where a
  transaction is split and the parent where it is not — summing both double-counts every split. The
  filter `type IN ('expense','income')` from 3.2 still applies on top.
- **Issue 4.3 (Need/Want/Invest)** should read nature per *line*, not per transaction: a supermarket
  trip is genuinely part need and part want, which is the whole reason this issue exists.
- **Splitting an existing transaction is not built.** There is still no edit path anywhere
  (3.1/3.2/3.3 are create-and-delete only); issue 3.6 owns it.
- **`observeRecent` still does not bound on `booked_on_iso_date <= today`** — carried over from 3.2,
  and issue 3.4 must revisit it.
- **The upgrade-path worktree** lives at `/c/cfo-v6`; short path because the scratchpad breaks
  Windows' limit, and removal needs `Remove-Item -LiteralPath '\\?\C:\cfo-v6' -Recurse -Force` after
  `git worktree remove` deregisters it.
