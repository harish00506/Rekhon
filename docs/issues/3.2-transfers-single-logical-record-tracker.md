## The requirement

**FR-TXN-003 (MUST)** — *"Transfers MUST be a single logical record affecting two accounts
atomically; deleting one side deletes both."* Plus **DB-004**: *"All multi-row operations (transfer,
split, import batch) run in a single transaction."*

## Scope decisions (agreed before coding)

| Decision | Why |
|---|---|
| **Branch order: commit 3.1 → merge to `dev` → branch 3.2** | 3.2 depends on 3.1, which was still uncommitted. Keeps 3.2's diff reviewable on its own. |
| **SRS-faithful schema: `type` *and* `transfer_id`** | The user's call. I recommended `transfer_id` alone, because `type` stores direction a second time and the two can drift. It does pay for itself: "money actually spent" becomes `type IN ('expense','income')` rather than a sign-and-null-check convention. **The drift risk is mitigated structurally, not by discipline** — see below. |
| **Delete affordance built now** | So the atomic both-legs delete is observable on a device rather than only in a test. Borrows a little from issue 3.6, which owns delete/bulk-edit properly. |
| **The list collapses a transfer to one row** | FR-TXN-003's "not two unlinked transactions". Two rows would read as ₹10,000 of activity for a ₹5,000 transfer. |
| **No `transfers` parent table** | It would carry no fact the legs don't already hold. Recorded as a deviation in [ADR-0008](../adr/0008-transfers-as-linked-legs.md). |
| **Cross-currency transfers refused, not converted** | Needs the `fx_rates` table §20.1 reserves and no issue has built. Guessing a rate would be the app inventing a number (P-03). |

**Scope boundary — not built:** splits (3.3), future dating (3.4), a source/type filter UI (3.5),
search/filters/bulk edit (3.6).

## The type/sign hazard, and what holds it

`type` and the amount's sign both record direction. §20.2 puts a `CHECK` constraint on the column,
but **SQLite cannot add one through `ALTER TABLE … ADD COLUMN`** and DB-003 forbids the destructive
rebuild that would be needed — so on every upgraded database that constraint cannot exist. Three
things stand in for it:

1. **No caller supplies a `type`.** It is derived inside `:data:repository` at one site per write
   path — the sign for expense/income, the leg for transfers, the reconciliation path for adjustment.
2. **`TransactionType.matches(amount)`** states the rule exactly once.
3. **`TransferTest.every row every write path produces has a type that agrees with its sign`** walks
   all four write paths and asserts it; `TransactionTypeTest` pins `matches` itself over the Long
   extremes, where a sign check written as `-amount > 0` breaks.

## Notes for later issues

- **A transfer's amount renders green**, because `CfoAmountText` colours by sign and the collapsed
  amount is positive. It carries no `+`, so it does not claim to be income, but a neutral colour
  would read better. Fixing it needs a new `CfoAmountText` mode and a Paparazzi baseline in
  `:core:designsystem` — deliberately out of scope here; fold it into issue 3.6 or 5.x.
- **`observeRecent` is a plain 30-day window and does not bound on `booked_on_iso_date <= today`.**
  Net worth's as-of query does. **Issue 3.4 (future-dating) must revisit it**, or a scheduled
  transfer will appear in the list before it has happened.
- **Issue 3.5** owns surfacing `source`/`type` to the user. 3.2 only made the values correct and
  parseable; nothing on screen yet says a row is an adjustment.
- **Issue 4.4** (budgets vs actuals) is the first thing that will compute a real spend total. It must
  filter `type IN ('expense','income')` — that filter is the whole reason the column was adopted.
- **The upgrade test needs a worktree at a short path.** `git worktree add /c/cfo-v5 dev` builds the
  previous APK; the scratchpad path breaks Windows' 260-character limit on the Paparazzi snapshot
  filenames. Removing it afterwards hits the same limit — `git worktree remove` deregisters it but
  leaves the directory, which needs `Remove-Item -LiteralPath '\\?\C:\cfo-v5' -Recurse -Force`.
  (Done for this issue; the repo is back to one worktree.)
