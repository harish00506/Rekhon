## What is genuinely unproven

Stated plainly, because this is the first issue where the headline AC could not be tested:

1. **That the database file is actually encrypted.** The code opens Room through SQLCipher's
   `SupportOpenHelperFactory`, which is the mechanism that encrypts it — but no test has confirmed
   the bytes on disk are ciphertext. `EncryptedDatabaseTest.theFileOnDiskIsCiphertext` asserts
   exactly that and is waiting for a device.
2. **That the Keystore path works at all.** `KeystoreAeadFactory` has never executed;
   `AndroidKeysetManager` needs a real Keystore. Every decision *around* it is unit-tested against
   Tink's own `Aead` interface, so the untested surface is one builder chain with no branches.
3. **That Room's generated code opens against a SQLCipher helper.** Compiles, never run.

Running `./gradlew :core:database:connectedDebugAndroidTest` on any device or emulator settles all
three at once.

## Decisions worth recording

- **Four tables, not thirteen** (your call). `profile`, `account`, `transactions`, `category` — the
  ones the AC names. Under DB-003 a wrong column guessed today costs a migration tomorrow, while a
  new table added later is a trivial non-destructive one, so building narrow is the cheaper error.
- **The key path is split so it can be tested at all.** SQLCipher needs passphrase bytes in memory;
  a Keystore key cannot be exported to become them. So a random passphrase is generated once,
  wrapped by a Keystore-backed Tink AEAD, and only the ciphertext is stored. Every decision lives
  in `SqlCipherPassphraseManager` behind Tink's `Aead` interface — unit-testable — leaving
  `KeystoreAeadFactory` as a branch-free platform binding.
- **An unwrap failure is an error, never a fresh passphrase.** If the Keystore key is gone (factory
  reset, lock-screen change) the app must say so. Minting a new passphrase would present an
  unopenable database as an empty one, and the user would see their finances silently wiped.
- **No `fallbackToDestructiveMigration`** (DB-003). There is no server copy; a missing migration
  must fail loudly at open, not drop tables.
- **StrongBox is not explicitly requested.** The `keystore-crypto` skill asks for it, but Tink's
  Android integration exposes no StrongBox flag, and selecting one means hand-building a
  `KeyGenParameterSpec` with `javax.crypto` — which SEC-003 forbids outright. Following the
  stronger rule: Tink only, TEE-backed master key, revisit if Tink adds first-class support.
- **DB re-key is deliberately absent.** `rotateWithPrevious()` supplies both keys and is tested,
  but the `PRAGMA rekey` execution is not written: an untested crypto path that rewrites the whole
  database is worse than an honest gap. It belongs with issue 11.1, on a machine with a device.
