## Acceptance criteria — how each is met

| Criterion | Evidence |
|---|---|
| The user sets the actual balance; the app computes the delta and records a labelled, source-tagged adjustment — never silently editing history | `AccountRepository.reconcile(accountId, statementBalance)` takes the **statement**, not a delta. It derives the balance inside its own `withTransaction`, subtracts, and writes one `TransactionEntity` with `source = "reconciliation"`. `history is never edited — the opening balance is untouched` pins the other half: the correction is additive, and the adjustment is soft-deletable like any other row (DB-002). |
| The adjustment is `Money` paise and shows before/after and the rule that fired (P-02) | `Reconciliation` carries `before`, `statement`, `delta` and the adjustment's id as one value, so a screen cannot render a delta belonging to a different balance than the one above it. The panel shows all three plus *"Adjustment = statement balance − app balance"* in words. Every amount is `Long` paise through `Money`'s overflow-checked `minus` (MNY-001); no division, so nothing to round. |
| Covered by tests including zero-delta and negative-delta | `AccountReconciliationTest` — 20 tests. Zero delta: **writes no row and mints no id**. Negative delta: proven on a credit card, the direction where a sign error would *increase* a debt the user was correcting downwards. |
| Golden rules; money/time rules hold | `booked_on_iso_date` from `clock.today()` in the profile zone, pinned by a test that sits at 18:30 UTC where the UTC and IST days differ (TIM-001/TIM-002); ids from the injected `IdGenerator` (P-08); the adjustment carries the **account's** profile so the demo wipe can reach it (ADR-0006); no network on any path, re-driven in airplane mode (P-04); the number comes from the store, never the screen (P-03). |
| DB-001's integrity job | `BalanceIntegrityWorker`, daily. One `UPDATE` re-derives every cache in the profile using a subquery identical to `observeWithBalances`'s; its trailing `<>` clause makes the row count mean *how many were wrong* rather than *how many exist*. `SessionLock` checked before anything injects (SEC-002), repository behind a `Provider`. |

## What is proven, and what is not

**Proven on a device, and checked by hand.** Three reconciliations, in both directions, with the
arithmetic done manually against the accounts list each time — and the *net worth* moved by exactly
the adjustment every time, which is the cross-check that the two figures come from the same rows.

**Proven on hardware: the second worker's locked path.** `RETRY → SUCCESS` in logcat, reached by
moving the device clock forward a day rather than by waiting. Worth recording as a technique: the
`jobscheduler run -f` route did not work — WorkManager's job ids are renumbered on every reschedule,
so the id in `dumpsys` was stale by the time the command ran.

**Found by running it, and only by running it — third issue in a row.** 2.5: a squeezed Delete
button. 2.6: the dashboard showing the stored snapshot. 2.7: a panel promising an adjustment it
could not make. Each was invisible to every unit test, and this one, like 2.6's, **could** be turned
into a gate and was.

**A design changed because of a test problem, and it was the right change anyway.** The dialog → panel
switch was forced by Robolectric never idling a `Dialog` window. It is recorded here rather than
buried because the alternative — keeping the modal and covering it only with instrumented tests —
would have left the screen unchecked on every ordinary run.

**Not built, and owned elsewhere.** Nothing yet *reads* `current_balance_minor`; every balance is
still derived. The job makes the column trustworthy, which is the precondition for switching the
read path onto it if the per-account subquery ever gets expensive — ADR-0007's open *Bad*
consequence about read cost stays open. A real `TransactionRepository` is Epic 3's; reconciliation's
insert is ~10 lines against the existing DAO and moves there unchanged.

**Still open:** CI has never run — there is no git remote, so every green remains a local green on
one Windows machine. Unchanged since 2.6, and still the project's largest gap.

**Worth knowing for the next issue:** this project now has a `Dialog`-shaped hole in its test setup.
Any modal added later will hang Robolectric the same way; prefer inline surfaces, or budget for an
instrumented test and say so in the tracker.
