## Acceptance Criteria

- [x] The reusable harness supports golden-file, property, and seeded-determinism tests for any engine (§21.5). In `:core:common`'s **test fixtures** — no new module and no new dependency, and test-only so ARC-002 is untouched. `GoldenFixture`/`GoldenRecord` for golden files, `SeededCases` for property tests, `assertDeterministic` for determinism. Added with `testImplementation(testFixtures(project(":core:common")))`.
- [x] The snapshot-update workflow is documented (`docs/testing/engine-test-harness.md` §5); determinism is enforced via an injected seed source (P-08) — `SeededCases` takes a fixed seed literal and `assertDeterministic` runs the subject **twice** at the same seed, which is the only thing that separates a deterministic engine from one reading a clock or a global `Random`.
- [x] At least one engine adopts it as a reference — `:domain:engines:card`: 41 lines of hand-written reader deleted, the fixture unchanged, and all 15 of its frozen records still asserted. The inherited guards were then demonstrated to bite (hiding the fixture, and emptying it, each fail the card test).
- [x] Golden rules respected. **P-08 is the point of half the harness.** MNY-001/002 are served rather than touched: the fixture format and the guide both state that amounts are paise and ratios basis points, and `longOrNull` returning `null` rather than `0` for an absent key exists precisely so a dropped amount cannot pass as a deliberate zero.
- [x] All Skill Rules and label-specific rules below are satisfied.
- [x] Definition of Done met (`00-issue-workflow.md` steps 9-11; `/pre-merge`).

**The decision worth reading first.** `GoldenSnapshot.propose` regenerates a fixture but **never writes it** — the candidate goes under `build/` and the test fails with a `cp` command. A flag that rewrote fixtures in place would be the most dangerous thing in this repository: set once in CI, every golden test in the project would pass for ever, rewriting its expectations to match whatever the code had started doing. Five vacuous gates have been found here already; none came with a switch.

## Workflow Rules — While Solving

### Universal (apply to every issue)

1. Define expected vs actual behaviour with evidence (logs, tests).
2. Reproduce before fixing; binary-search to isolate the root cause.
3. Form testable hypotheses; switch to formal debugging after 10 min of guessing.
4. Smallest correct diff; match the surrounding code style.
5. Verify the fix with the original reproduction case.
6. **Respect the boundaries** - `feature → domain → data/core` (ARC-001); engines pure-Kotlin (ARC-002); repositories are the only DAO touchers (ARC-005).
