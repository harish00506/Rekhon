### Phase 3 — what actually happened, honestly

**The engine's implementation was written before its tests, not after.** The workflow asks for
red-first and this did not do that. What stood in for it was **mutation testing**: once the suite
was green, eleven separate breakages were applied to the engine and the rulebook and each was
confirmed to turn a specific test red.

That run was not a formality — **it found three tests passing for the wrong reason**, which a
red-first ordering would not have caught either:

- `the balance is never taken as the amount` passed because the balance happened to be the *second*
  figure and the parser takes the first. Dropping the balance guard entirely left it green. Fixed by
  asserting the confidence too, and by adding an alert whose *only* figure is a balance.
- `a merchant whose name contains bal keeps its amount` put the merchant *after* the figure, so the
  substring landed outside the window being searched. Rewritten with the name first.
- `the earliest keyword decides the direction` used "credit card", which is not the whole word
  `credited` — so no credit keyword matched and the tie-break never ran. Replaced with a transfer
  alert naming both verbs, and a refund-for-a-purchase.

Two further gaps were closed the same way: nothing proved the currency-marker requirement (a
reference number could have become money), and nothing proved "first, not largest" (added a fee
notice whose second figure is larger).

**Lesson for the next issue:** write the test first *and* mutate it. Red-first proves the test can
fail; mutation proves it fails **for the reason the name claims**.

## What the security review found

Both findings are the same shape — **a new profile-scoped table that device-wide machinery did not
know about** — and neither was caught by a test, which is the part worth remembering.

1. **The demo wipe did not reach `sms_draft`** (would have been a P-01 / ADR-0006 violation). The
   daily scan writes drafts against whichever profile is active, so a demo session on a phone whose
   owner had opted in would leave inferences drawn from their *real* inbox behind, under a profile
   that had been destroyed.

   **Why no test caught it:** `DemoModeRepositoryTest` asserts "zero rows remain across every table"
   using `DemoDao.countRowsFor` — a query that enumerates the same table list `DemoDao` deletes. A
   table missing from the DAO is therefore missing from the count too, and the assertion passes
   vacuously. The test's own doc warns about this exact failure for issue 2.6's
   `net_worth_snapshot`, and it happened again anyway. **Adding a profile-scoped table means editing
   three places: the delete, the count, and a test.**

2. **Revocation was scoped to the active profile.** The consent is device-wide, so revoking while
   the demo was showing would have kept every pending draft under the real profile —
   `onConsentRevoked`'s own doc claimed it erased "every pending proposal". Now
   `SmsDraftDao.deleteAllPending()`, the only deliberately unscoped query in this schema.

Both fixes carry a regression test that was verified to fail without them.

### Phase 7 — what the device did and did not prove

**Proved on the emulator (API 34):** the 11→12 migration against real SQLite including the unique
index and the revocation delete; that the app installs and boots on the migrated schema; and — the
check worth having for this issue — that the **built APK declares `READ_SMS` denied-by-default and
does not declare `RECEIVE_SMS` at all**, which is ADR-0013's mitigation verified on the artifact
rather than in the source.

**Also proved, after the first attempt failed:** `SmsInboxDeviceTest` now runs the real reader
against Android's own `Telephony.Sms.Inbox` — the projection is accepted, `_ID > ?` really excludes
what has been read, and the `LIMIT` inside the sort order is really honoured. That is the class of
assumption a fake provider can never check, because a fake we wrote answers whatever we ask it.
Verified to bite by naming a column the provider does not have.

**Still not proved:** that a real bank alert *as the provider stores it* parses correctly — the
platform could normalise whitespace or split a long message across rows. Two routes to seeding the
inbox were tried and both are blocked on a stock AVD, which is why the test documents them:

- **Writing directly** — since KitKat only the *default SMS app* may write to the telephony
  provider, so an instrumentation test cannot insert rows.
- **`adb emu sms send`** — goes through the modem, but needs an initialised default SMS app to
  persist. Granting the SMS role to Google Messages (`cmd role add-role-holder`) was **not enough**:
  the role showed as held, three alerts were sent, and `content://sms/inbox` stayed empty, because
  Messages had never been through its own setup.

**Closing it needs an AVD with Messaging actually set up, or a physical device**, and it should
happen before this reaches `stage`. The test is written so that it exercises the parse
automatically on any device that does have messages.

## Known gaps, recorded rather than hidden

1. **`onConsentRevoked()` has no caller.** It erases pending drafts and resets the scan cursor, and
   the consents dashboard that will call it is issue 5.x's. Revoking today stops all reading
   immediately (the gate holds, and `observePending` emits empty), but existing pending rows stay on
   disk until that screen lands. Recorded in ADR-0013's consequences.
2. **A draft's amount cannot be edited before accepting it.** A flagged draft can be accepted as read
   or dismissed; correcting a misread figure means dismissing it and typing the transaction. The
   review screen deliberately has no per-row edit state — adding one is a follow-up, not a
   correctness gap, since the parser refuses rather than guesses.
3. **The 95% eval thresholds are ours, not the SRS's.** §18.1 gives OCR a number and the SRS gives
   SMS none. Stated in `ENGINE.md` and in `SmsEvalTest`'s class doc so nobody later cites them as a
   requirement.
4. **`READ_SMS` may block a Play release.** ADR-0013, with the fallback.
