## Decisions worth recording

- **Programmer errors are rethrown, not converted.** §21.6 pulls both ways — "no exceptions across
  layer boundaries" against "crashes only for programmer errors". `runCatchingToResult` converts
  I/O-ish failures but lets `IllegalStateException`/`IllegalArgumentException` escape, so a failed
  `require`/`check` crashes loudly instead of reaching the user as a generic "something went wrong"
  and going unnoticed. Pinned by a test so a later refactor cannot quietly reverse it.
- **`CancellationException` and `Error` always propagate.** Not a preference: swallowing
  cancellation tells a cancelled coroutine it merely failed, so it keeps running — a silent
  structured-concurrency leak (ARC-006). Also test-pinned.
- **No PII by construction, not by review (P-01, AC4).** `toAppError()` is the only path from a
  `Throwable` to an `AppError`, and it keeps the exception's **class name** and discards its
  message — exception messages routinely carry file paths, URLs with tokens, or the failing row.
  A test feeds in `IOException("failed writing ₹1,23,456.78 for account 9876543210")` and asserts
  neither the account number nor the amount survives.
- **`message` is a non-localised fallback; `code` is the lookup key.** Localised copy lives at the
  UI edge (task 1.1.4 §4), so a pure-Kotlin module can carry error semantics without owning
  user-visible strings — the same tension the ₹ symbol raised in issue 1.2, resolved properly here.
- **`Result` shadows `kotlin.Result` inside the package.** Accepted — the SRS names the type — and
  `runCatchingToResult` exists so no call site needs the stdlib one.
- **No Arrow.** Task §4 rules it out; a sealed interface plus nine combinators is smaller than the
  dependency, and adding one would need an ADR.
