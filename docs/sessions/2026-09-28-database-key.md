## 1 · Decisions this session

The full argument for each is in [ADR-0057](../adr/0057-the-database-key-lives-in-the-strongest-place-the-phone-has-and-rotates-without-losing-the-database.md).

- **The master key is generated by the platform, StrongBox first, before Tink looks for it.** Tink
  has no StrongBox option, so a phone with a security chip was getting an ordinary TEE key. Asking
  the platform's own `KeyGenerator` for the key at that alias first is not hand-rolled crypto — it
  is the same call Tink makes, with one flag. **Issue 1.6's note saying otherwise was wrong and has
  been corrected in place**; leaving a contradictory claim in the codebase would be worse than
  either choice.
- **An existing alias is never replaced.** The first branch of `MasterKeyPolicy`, and the one that
  protects every installation that already has data: the keyset is encrypted with the master key,
  the passphrase with the keyset, the database with the passphrase. A new key at that alias is
  silent, total, unrecoverable loss — on an *upgrade*.
- **Rotation has two slots, because a rotation is two writes and a process can die between them.**
  Stage the new key → `changePassword` the file → promote. Both keys are on disk throughout, so a
  crash anywhere inside the window is recovered by the next open, which tries both candidates and
  reports which one worked. A re-key that reports failure rolls the staging back, because the file
  is still on the old key.
- **The promotion is a rename**, so it cannot be interrupted into the state where neither key
  exists. **The re-key is SQLCipher's own `changePassword`**, never a hand-built `PRAGMA rekey`
  string — composing that would mean formatting key material into SQL text.
- **A key that no longer opens anything is zeroed** — after a successful rotation, and for the
  candidate that lost the race at open. After a *failed* rotation the old key is deliberately kept:
  the file still needs it.
- **Deferred** (ADR-0057): a UI that rotates the key (it belongs beside erase-all and the consents
  dashboard, 11.3/11.4); a cryptoperiod; re-keying Tink's own keyset; and StrongBox proven on real
  hardware.

**What the work turned up.**

1. **The `rotate()` that shipped in issue 1.6 would have destroyed a database.** It replaced the
   stored passphrase and nothing re-keyed the file, so the first caller would have left the
   database encrypted with a key the app had just thrown away. It was never called — that is the
   only reason it never happened. It has been replaced by a rotation that takes the re-key as its
   middle step and cannot be invoked without one.
2. **The security review verified a library assumption instead of trusting it.** The recovery path
   tries one passphrase and then another, and then compares the winner — all of which would break
   if SQLCipher zeroed the caller's array. It does not; that was checked in the 4.6.1 artifact's
   bytecode, and it is written down in the ADR so the next person does not have to re-derive it.
3. **Lint caught a real API-level trap.** `StrongBoxUnavailableException` is API 28, and a `catch`
   of a class the platform does not have is a load-time failure rather than a dead branch. The
   enum already made it unreachable below 28; the version check is now visible at the call site
   too, which is what a reader needs.

## 2 · Flow changed this session

The key path, now with a recovery branch and a rotation — `FLOW.md` §2.20:

```
CfoDatabaseFactory.open
└─ KeystoreMasterKey.ensure → MasterKeyPolicy      keep existing · StrongBox · Keystore
└─ SqlCipherPassphraseManager.candidates()         current + (pending, only mid-rotation)
   ├─ try current → forced Room open               a wrong key must surface here, not later
   ├─ else try pending
   └─ confirm(whichever opened)                    promote or discard; the loser is zeroed

CfoDatabaseFactory.rotateKey                       no CfoDatabase may be open
└─ rotate { DatabaseRekeyer.rekey(file, change) }  stage → re-key → promote
```
